## Ce que ça change, en clair

- **La pastille reste, telle qu'aujourd'hui.** Pour une session marquée `pastille` et hors Desktop,
  tu cliques « Démarrer localement », et c'est toi qui préviens l'orchestrateur à la fin. On arrête
  les preuves sur ce sujet (P13, P14, P15) : l'orchestrateur n'ouvrira pas lui-même ces sessions.
- **L'idée est reportée, pas jetée.** Elle se rouvre sur un signal précis (plus bas), pas sur l'envie :
  tant qu'il n'est pas là, ne pas la rejuger.
- **Le chantier des mods démarre, et absorbe `claude-mods`.** O1 (modèle de l'index imposé), O3
  (`run_in_background: false` par défaut), O5 (ligne d'état), plus les quatre mods prévus par le
  projet `claude-mods` (limites, fichiers, plan, incidents) vivent dans `plugin/mods/`, en **deux
  mini-plugins** : **garde-fous** (O1, O3) et **affichage** (le reste). Publiés à la même version
  que le workflow, `/maj-workflow` et `/migrer-projet` les installent ensemble dans chaque projet.
  Ce que tu verras : rien à installer à la main, sur aucun poste ; plus de marketplace à part.
  Revers : chaque changement d'un mod demande une nouvelle version, sans quoi le module n'est pas
  rechargé (P12), et n'atteint un projet qu'à son prochain `/maj-workflow` (frontière de plan).

## Ce qui est tranché, et pourquoi

### La session neuve ne remplacerait aucune pastille réelle

En Desktop, la voie normale est le **sous-agent**, sans pastille (`WORKFLOW.md` §5b). La pastille ne
sert que dans deux cas :

1. **Hors Desktop** (VSCode, terminal, cloud) : la tâche planifiée est un mécanisme de Desktop, elle
   n'y existe pas.
2. **En Desktop, une session marquée `pastille`** : le cadreur la pose quand le N1 de la session est
   structurant et mérite un déroulé surveillé (`/nouveau-plan`, mots-clés d'exception). Or une tâche
   planifiée **ne peut pas lancer le serveur de dev** : « Dev servers can't be started from unattended
   sessions (scheduled-task runs and remote-dispatched trees) — nobody is present to approve the
   command. » (EBM-MSPv2, P9/S3 et P9/S4).

Le seul cas Desktop où la pastille sert est donc celui qu'une tâche planifiée ne peut pas jouer.
Même une P16 entièrement positive (permission, réveil, archivage) ne retirerait aucune pastille :
le blocage est de principe, pas un réglage manquant.

Options écartées : **abandonner sans signal** (l'utilisateur préfère garder la porte ouverte) ;
**poursuivre par P16** (environ 100 tours pour un résultat qui ne couvre pas les sessions `pastille`).

Décidé par l'utilisateur, 2026-10-06 : reporter avec un signal.

### Signal qui rouvre l'idée

Les **deux** ensemble, constatés dans la documentation ou les descriptions d'outils de Desktop :

- une session sans surveillance (tâche planifiée ou équivalent) peut lancer le serveur de dev et
  utiliser le navigateur in-app ;
- une session lancée par une autre **prévient son lanceur à sa fin**, de façon documentée (par
  exemple une session liée `start_session`, citée par les outils mais absente en 2026-10).

À la réouverture, reste aussi à résoudre la permission : une session planifiée tourne en `default`,
pas dans le mode de son lanceur (P15, mesure P).

### Ce que P15 laisse d'acquis, sans usage pour l'instant

Lancer une tâche planifiée et la suivre en Remote Control sans approbation (R) ; la régler au modèle
voulu par `model:` dans son `SKILL.md` (M, non documenté) et à l'effort voulu par `modelSettings`
(E). Le correctif du hook Stop (0.55.0 : jamais de relance d'une session planifiée) reste utile aux
tâches planifiées ordinaires, comme les pré-collectes d'EBM-MSPv2.

### Les mods : voie du mini-plugin

K est négatif (rejoué le 2026-10-06 après reconnexion) : une clé `modules` dans le
`.claude/settings.json` d'un projet n'est pas lue, le même module installé en plugin l'est. La
branche « sauf si K est positive » de `2026-10-06-suite-des-preuves-mods.md` tombe : la voie du
mini-plugin, déjà décrite dans cette décision (source `plugin/mods/` avec son
`.claude-plugin/plugin.json`, publication par `publier.mjs`, vendoring dans `.claude/workflow/mods/`,
installation `--scope local` par `/maj-workflow` et `/migrer-projet`), s'applique telle quelle,
avec le périmètre élargi ci-dessous. `/nouveau-plan` découpe.

### Périmètre élargi : `claude-mods` absorbé, deux mini-plugins

Décidé par l'utilisateur (2026-10-06), sur le constat que **chaque projet reçoit le workflow
vendoré** : le motif qui gardait `claude-mods` à part (mods visibles hors des projets du workflow,
activés au niveau utilisateur) ne vaut plus que pour les sessions ouvertes hors projet.

- **Absorbés** : les quatre mods du MVP de `C:\Users\Kovu\Projets\claude-mods\PROJECT_BRIEF.md` —
  **limites** (5 h et 7 j, pourcentage et heure de reset), **fichiers** (état git : modifié, nouveau,
  commité non poussé), **plan** (panneau du plan, statut des sessions, prochaine action, boutons de
  relance), **incidents** (rassembler les incidents des projets). Ce brief (MVP, contraintes de
  rendu Desktop et mobile, risques, stratégie de test) est une donnée d'entrée du plan. Le projet
  `claude-mods`, sans code, est clos (sa décision d'absorption y est écrite).
- **Deux mini-plugins, installés ensemble** : un plugin n'admet qu'un module (P13, S5), et un module
  refusé au chargement se tait sans erreur (P12). Tout fondre en un module ferait qu'un bug
  d'affichage désactive O1 sans signe visible. D'où **garde-fous** (O1, O3 : rarement modifiés) et
  **affichage** (O5, limites, fichiers, plan, incidents : évolue souvent).
- **Une seule ligne d'état** : O5 et limites se conçoivent ensemble, plus de recouvrement à arbitrer.
- **Ce qui disparaît** : la marketplace GitHub de `claude-mods`, son `installer.ps1`, l'activation
  dans les settings utilisateur. Revers : hors d'un projet du workflow (dossier `Projets` lui-même),
  aucun mod ne s'affiche.
- Suggestion de découpe, non imposée : distribution et garde-fous d'abord, affichage ensuite.

Réserve de K, à garder en tête dans le plan : le projet de fixture n'était pas approuvé
(`hasTrustDialogAccepted`) ; le témoin montre qu'un module **de plugin** se charge quand même.
