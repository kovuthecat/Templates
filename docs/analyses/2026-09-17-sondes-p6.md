## A — effort d'agent (geste utilisateur demandé)

Tentative en session : création de `.claude/agents/sonde-effort.md` (`model: haiku`, `effort: high`,
prompt « réponds OK »), puis appel `Agent` avec `subagent_type: sonde-effort`.

**Constat intermédiaire (environnement) :** l'appel a échoué —
`Agent type 'sonde-effort' not found. Available agents: claude, claude-code-guide, Explore,
general-purpose, Plan, statusline-setup, workflow:explorateur, workflow:lecteur-doc,
workflow:resumeur-git, workflow:verificateur-n0`. La liste des agents disponibles pour l'outil
`Agent` est chargée au démarrage de la session, pas relue à chaud : un agent créé en cours de
session n'est pas utilisable dans **cette** session. C'est une contrainte d'outillage
supplémentaire, non documentée dans la décision d'entrée — à signaler séparément (nature
`environnement`).

Le fichier `.claude/agents/sonde-effort.md` a été recréé après ce constat ; l'utilisateur a accepté
de faire le geste dans une **nouvelle** session Desktop sur ce même dossier (seul moyen de charger
l'agent), d'y lancer `sonde-effort`, et de lire le panneau des tâches pendant/après son exécution.

**Constat posé** : le lancement a réussi dans cette nouvelle session (agent chargé, exécuté en 2s,
réponse « OK »). La carte « Terminé » et le détail de transcription affichent le modèle
(`Modèle Haiku 4.5`, conforme au frontmatter) mais n'affichent l'effort nulle part — conclusion
`NON SONDABLE ICI` (voir table ci-dessus).

Suivant : supprimer `.claude/agents/sonde-effort.md` (agent jetable, sonde close).

## C — session cloud, hooks et push (geste utilisateur demandé)

L'utilisateur a accepté d'ouvrir une session cloud sur un dépôt vendoré de test (pas Templates), d'y
observer si le bloc « règles communes injectées par le plugin workflow » apparaît au démarrage
(comme dans cette session), puis de tenter `git push origin HEAD:main` d'un commit **vide** sur une
branche jetable de ce dépôt de test.

**Constats bruts rapportés par l'utilisateur :**

1. **Bloc visible au démarrage** : oui. Apparu comme contexte additionnel `SessionStart hook`, avec
   le commentaire `<!-- règles communes injectées par le plugin workflow -->` suivi du contenu de
   `CLAUDE-BASE.md` et de l'état du contexte projet (retard `STATUS.md`, rappel de branche).
2. **Push** : accepté. `git push origin HEAD:main` depuis la branche jetable
   `test/push-guard-check-1789649802` (commit vide `a4b6404`, précédent `cbbe1e9`) — sortie
   `To https://github.com/kovuthecat/Myo cbbe1e9..a4b6404 HEAD -> main`, exit code `0`. Le commit de
   test est réellement sur `main` du dépôt de test (`kovuthecat/myo`).

**Conclusion : CONFIRMÉE** — bloc présent et push accepté → C3 peut autoriser le push direct sur
`main` depuis une session cloud, sous les mêmes conditions que localement.

**Réserve de gouvernance à porter à l'attention du plan (S3/S5/S7, hors périmètre d'écriture de
cette session) :** aucune protection de branche GitHub ni garde-fou technique (hook Git bloquant)
n'a empêché ce push — le bloc contextuel lui-même précise que « le travail de ce workflow vit et se
pousse sur `main`, session cloud comprise », donc l'autorisation vient d'une **instruction** (texte
lu par l'agent), pas d'un **mécanisme** (hook, branch protection). C3 étend une règle qui n'est
aujourd'hui tenue que par la lecture du contexte : rien n'empêcherait un push involontaire côté
cloud si le contexte n'était pas lu ou mal interprété. À signaler explicitement au relecteur de plan
avant d'écrire l'extension de C3 dans `plugin/` (S3/S5/S7).

## Constat hors périmètre des quatre sondes — cache plugin du poste (T2)

Pendant la lecture du contexte de session, le hook `SessionStart` de cette session annonce
« STATUS.md a 137 commits de retard » — alors que `STATUS.md` est supprimé du dépôt Templates
depuis le commit `f0444c6` (`git log --oneline -1 -- STATUS.md`). Le message vient donc d'un
plugin `workflow` **différent** de celui vendoré dans ce dépôt (`plugin/`, source à jour 0.38.1) et
différent aussi du dossier `~/.claude/plugins/cache` (vide de tout plugin `workflow` — la commande
`node plugin/bin/sync-workflow.mjs --source plugin --projet . --check` ne voit que la copie
vendorée locale de ce dépôt sur elle-même, 52 fichiers à écrire, 0 ligne `CACHE`).

**Localisation confirmée** (lecture directe du fichier, pas seulement rapportée) :
`C:\Users\Kovu\AppData\Roaming\Claude\local-agent-mode-sessions\2ffc1972-69ba-47f7-b1d5-f6c0ef15f4aa\56975046-a0fe-4693-9398-65f93f0d224a\rpm\plugin_01S1aHm8xtRQTuVG3hVF5FCe\`.
Contenu de `.claude-plugin/plugin.json` :

```json
{
  "name": "workflow",
  "description": "Workflow perso Thibault : plans multi-sessions, validation N0-N2, contexte plafonné.",
  "version": "0.1.0",

  "skills": "./.claude/skills/",
  "hooks": "./.claude/hooks/hooks.json"

```

C'est un plugin **de compte**, géré par l'app Desktop (pas par ce dépôt ni par
`~/.claude/plugins/cache`), instantané figé du dépôt Templates au **2026-09-02** (date de
modification du fichier) — antérieur de plusieurs semaines à la 0.38.1 source. Son dossier
`.claude/skills/` ne liste que six skills : `choisir-mecanisme`, `fin-de-tache`, `nouveau-plan`,
`nouveau-projet`, `purge-contexte`, `verif-visuelle` — exactement la liste des skills `workflow:*`
disponibles dans **cette** session (sans `cadrer`, `orchestrer-plan`, `maj-workflow`), et son
dossier racine contient encore `STATUS.md` : preuve directe que c'est ce plugin, et non celui de
`plugin/`, que la session Desktop charge en `inline` — confirmé par `~/.claude.json` :
`pluginUsage["workflow@inline"].usageCount = 16686`, un compteur d'usage bien trop élevé pour un
plugin secondaire.

**Défaut mesuré, hors du périmètre de cette session** (ni écriture sous `plugin/`, ni sous
`%APPDATA%`) : `sync-workflow.mjs --check` ne voit pas cet emplacement — il ne compare que
la copie vendorée du projet courant à `plugin/`, jamais le plugin de compte injecté par l'app
Desktop. Une mise à jour de `plugin/` (comme celle de ce plan, 0.38.1) ne rafraîchit donc jamais ce
plugin `inline` : seul un geste dans l'app (Personnaliser → Plugins) le fait, et rien dans ce dépôt
ne peut le déclencher ni le vérifier automatiquement. À consigner comme incident de nature
`environnement`, hors correctif localisé (le remède n'est pas dans la zone de ce dépôt).

**Retrait** : dossier géré par l'app Desktop, à ne pas modifier ni supprimer directement — le
retrait ou la mise à jour se fait par l'utilisateur dans Desktop → Personnaliser → Plugins.
