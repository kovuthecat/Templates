## Constats établis au cadrage (2026-10-05, doc bundlée 2.1.286 — à recontrôler, l'API bouge)
- Un plugin déclare ses function hooks dans **un** module, que `hooks/hooks.json` nomme sous
  `"modules": ["./<fichier>"]`. Ce chemin est relatif à `hooks.json`.
- Seuls `--plugin-dir`, `CLAUDE_CODE_PLUGIN_DIRS` et les plugins de dossier skills sont surveillés
  et rechargés à chaud. Un plugin installé par marketplace (le cas de `workflow`, `--scope local`)
  ne charge qu'au **démarrage** d'une conversation.
- `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` n'est mentionné que pour `claude -p`.
- `turn.complete` porte `usage` (input, output, cache read, cache creation). `agentId` est présent
  sur `session.append` ; pour `tool.call` et `turn.complete`, c'est à vérifier dans les types.

## Hors périmètre
- Les cinq hooks commande (`plugin/hooks/*.mjs`) : on n'y touche pas. Ils sont la référence de M1
  et de M2.
- Aucun `deny` ni aucune réécriture dans le mod : il observe seulement. Tout hook appelle `next(e)`
  et rend son résultat tel quel. Exception : M3b, en T4, sur une copie séparée.
- Rien sur `main`, aucune publication, aucun bump de `plugin.json` `version`, aucun
  `publier.mjs` sans `--dry-run`.
- Ne pas installer de marketplace de compte (claude.ai). Seule l'installation `--scope local`
  existante sert (`CLAUDE.md`).
- Les instruments restent contestables : `tester-hooks.mjs`, `n0.mjs` et `prochaine-action.mjs`. Un
  défaut qu'ils révèlent se note en T5.

## T2 — M1 : le mod charge-t-il sans réglage ?

### Objectif
Dans la conversation neuve, constater si le module a chargé et si les cinq hooks commande sont
intacts.

### Pourquoi
Si un mod exige une variable ou un second fichier, chaque projet paie un coût de distribution.
C'est le premier critère de l'adoption.

### Décision clé
Décision § M1 :
- **positif** : `session.start` du mod s'exécute et les cinq hooks restent actifs ;
- **négatif** : il faut une variable, un hot-reload ou un second fichier, ou un hook casse. Le coût
  est alors chiffré par projet.

### Lire / Modifier
- Lire : `plugin/templates/project-settings.json` — câblage vendoré, sans fichier de câblage plugin.
- Hors dépôt, à lire aussi : le journal du mod, ~/.claude/preuves/mods/journal.jsonl.

### Étapes
1. **Premier geste** : `git branch --show-current` → `preuve/mods`. Vérifier aussi que la
   conversation est neuve : aucun échange avant `/reprendre`. Sinon, `FAIL` environnement.
2. Lire `journal.jsonl` : une trace `session.start` postérieure au commit de T1 ?
3. CLAUDE-BASE injecté ? (Ses règles apparaissent dans le contexte de session : citer une ligne.)

## T3 — M2 : le mod voit-il les outils des sous-agents ?

### Objectif
Faire lancer `git commit` par un sous-agent sous un `wave.lock` factice. Relever si le mod voit
`agentId` et si le PreToolUse classique se déclenche.

### Pourquoi
Si le mod voit ce que le hook classique laisse passer, une garde git par mod comble l'incident
du 2026-09-17. Sinon, il n'y a aucun gain de fiabilité à attendre.

### Décision clé
Décision § M2 :
- **positif** : `agentId` est présent et le hook classique reste muet ;
- **négatif** : `agentId` est absent, ou le hook classique se déclenche déjà. Dans ce dernier cas,
  la prémisse de l'incident est réfutée : c'est à écrire.

### Lire / Modifier
- Lire : `plugin/hooks/pretooluse-git.mjs` — le cas de refus sous verrou.
- Hors dépôt, à lire aussi : le journal du mod, ~/.claude/preuves/mods/journal.jsonl.

### Étapes
1. Sur `preuve/mods`, écrire `.claude/wave.lock` (contenu « preuve P12 M2 »). Il n'est jamais
   commité : vérifier `git status`.
2. Lancer `Agent({ subagent_type: "workflow:session-low", run_in_background: false, prompt:
   "Exécute exactement : git commit --allow-empty -m 'preuve M2'. Rapporte la sortie brute." })`.
   Repli si le type est introuvable : `session-low`, puis `general-purpose` + `model: "haiku"`.
3. Relever trois choses :
   - la sortie du sous-agent : refus du hook classique, ou commit créé ;
   - `git log -1` ;
   - les lignes `tool.call` du journal, avec ou sans `agentId`.
4. Supprimer `.claude/wave.lock`. Si un commit `preuve M2` a été créé, le laisser : la branche est
   jetable, et il est la preuve.

## T4 — M3 coût d'un plan · M4 affichage de l'état

### Objectif
Rejouer deux fois le même petit plan orchestré et agréger l'usage par `agentId`. Dans le même
déroulé, afficher l'état du plan dans un `Pane` ou un `AbovePrompt`.

### Pourquoi
Le workflow n'a aucun chiffre de coût. Si le mod sait dire où part la dépense, les leviers de
réduction se jugent sur pièce ; sinon, ils restent spéculatifs. Le même déroulé sert M4 sans
payer un second plan.

### Décision clé
- **M3**, positif : écart < 15 % entre les deux exécutions et poste dominant identifié
  (orchestrateur, sessions ou préfixe système). Négatif : usage absent ou incomplet pour les
  sous-agents.
- **M4**, positif : l'état est visible et à jour sans rien demander, et aucune ligne de refus
  n'apparaît dans le transcript. Négatif : rien n'est rendu dans Desktop, ou `$.process` est refusé
  et `$.fs` ne suffit pas.

  conversation pour que le mod voie ses sous-agents.
