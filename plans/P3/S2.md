## T4 — Écrire `skills/orchestrer-plan/SKILL.md`

### Objectif

La skill déroule **un plan entier**, vague après vague, sans rendre la main entre elles. ≤ 250 lignes.

### Décision clé — trois politiques, à respecter à la lettre

**1. Boucle, pas récursion.** Lire l'`index.md` une fois, en extraire les vagues déclarées et leurs
sessions. Puis, pour chaque vague dans l'ordre : lancer → collecter → cocher les statuts → passer à
la suivante. Les vagues déclarées font foi (leur parallélisabilité encode un jugement de zones que
le cadrage porte, pas l'orchestrateur).

**2. Politique d'échec — finir la vague, arrêter le plan.** Un `FAIL` ne tue pas les sous-agents
déjà lancés de la vague en cours : ils vont au bout (on ne peut pas les rappeler, et leur travail
est déjà commencé). La vague est collectée normalement, puis **le plan s'arrête** : la vague
suivante n'est pas lancée. Le rapport distingue explicitement les sessions **bloquées par l'échec**
(celles qui en dépendent, directement ou transitivement) des sessions **encore indépendantes** —
c'est ce qui permet à l'utilisateur de décider s'il répare d'abord ou s'il relance le reste.

**3. Gate humaine.** Une vague dont la ligne d'ordonnancement porte le mot **`gate`** arrête
l'orchestrateur **après** l'avoir collectée, même si tout est `PASS` : il rend la main avec l'état
et ce qui reste. C'est l'échappatoire qui préserve le critère « gate humaine entre deux tâches » du
cadrage (validation N2, arbitrage produit) maintenant qu'il n'y a plus d'arrêt automatique.

### Lire / Modifier

- Créer : `plugin/skills/orchestrer-plan/SKILL.md`. Frontmatter : `name: orchestrer-plan`,
  `model: haiku`, description **une ligne** disant quoi + quand.
- Ne pas toucher à `skills/executer-vague/` (hors périmètre).

### Étapes

1. Structure imposée, dans cet ordre : **Interdits** (inchangés dans l'esprit : ne jamais ouvrir un
   `S<k>.md`, ne jamais lire un diff, ne jamais corriger, ne jamais interpréter un rapport) →
   **Étape 1** lire l'index (vagues, sessions, `Env.`, dépendances, gates) → **Étape 2** préflight
   (arbre sale ; verrou si la vague est parallèle ; le préflight CLI/trust/allowlist ne concerne QUE
   les sessions `Env. = headless` déclarées) → **Étape 3** lancer (sous-agents par défaut ; bloc
   headless court pour les déclarées ; repli pastille hors Desktop) → **Étape 4** collecter (verdict
   = commits, cf. §4b ; le motif vient de la ligne de l'agent ou du JSON s'il est lisible) →
   **Étape 5** statuts + vague suivante, ou arrêt (échec / gate / fin de plan) → **Étape 6** rapport.
2. Le lecteur JSON tombe à ~30 lignes : plus de verdict `PANNE` élaboré, plus de fail-closed à trois
   branches — un JSON illisible est un **motif absent**, les commits jugent (§4b).
3. Garder le diagnostic escaladé (Étape 5b actuelle) en ~15 lignes.
4. Toute règle de §4a/4b/5b → **renvoi**, jamais reformulation.
