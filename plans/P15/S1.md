## T1 — Une session planifiée ne reçoit jamais `decision: block` du hook Stop

### Objectif
Quand la session qui s'arrête a été lancée par une tâche planifiée, le hook Stop rend au plus un
rappel non bloquant (`systemMessage`), jamais `decision: block`. Puis bump 0.55.0, CHANGELOG,
publication, plugin local à jour.

### Pourquoi
Une session planifiée n'a personne pour lire le blocage : il la relance pour un tour de plus, après
son verdict. En P13, les deux sessions ont été relancées pour « travail non poussé » ; en P14, pour un
plafond de `TASKS.md`. Cela fausse le nombre de tours que P15 mesure (leçon 5), et, une fois la voie
adoptée, ferait payer un tour inutile à chaque session de plan lancée par l'orchestrateur.

### Décision clé
- **Détection** (constatée sur `~/.claude/projects/C--Users-kovu-Projets-Templates/b15f6ba1-ee4a-4a6c-882d-5ae74256cb35.jsonl`,
  session planifiée de P14) : le transcript contient, **en tête**, un enregistrement
  `{"type":"queue-operation","operation":"enqueue","content":"<scheduled-task name=\"p94-b\" file=…>…"}`.
  Il n'est **pas forcément en ligne 1** : dans ce fichier, la ligne 3 (SessionStart) porte un
  horodatage antérieur à la ligne 1 — l'ordre du fichier ne suit pas les horodatages.
- Règle : lire `entree.transcript_path` (champ documenté de l'entrée du hook Stop), **tête bornée**
  (64 Kio au plus), parcourir les enregistrements JSON ligne à ligne **jusqu'au premier enregistrement
  `type: "user"` ou `type: "assistant"` exclu** ; session planifiée ssi l'un d'eux est un
  `queue-operation` / `enqueue` dont `content` (chaîne) commence par `<scheduled-task name=`.
  Ligne illisible : ignorée. Fichier absent, illisible, ou champ absent → **non planifiée** (le
  comportement d'aujourd'hui) : un faux positif retirerait la garde à une session interactive, un faux
  négatif ne coûte qu'un tour.
- Fonction `estSessionPlanifiee(transcriptPath)` dans `plugin/hooks/lib.mjs` (exportée, sans
  dépendance, ne lève jamais).
- Dans `stop-contexte.mjs` : session planifiée → mêmes vérifications, mais **aucun chemin** ne
  rend `decision: 'block'`. S'il y a des problèmes : un `systemMessage` qui commence par
  `⚠ Session planifiée — rappel non bloquant :` puis la liste, émis une fois (même marqueur
  anti-répétition que les rappels existants : même empreinte → silence). Avertissements seuls :
  inchangé. Mettre à jour le commentaire d'en-tête (une exemption de plus, avec sa raison).
- **Revers assumé** (à écrire dans le CHANGELOG) : une session planifiée que l'utilisateur reprend
  ensuite à la main n'a plus que ce rappel, jamais le blocage.
- Version : `0.55.0` dans `plugin/.claude-plugin/plugin.json` (seule source de version).
  CHANGELOG : une ligne datée `2026-10-06`, forme des entrées existantes (titre en gras, plugin
  `workflow` 0.55.0, cause P13/P14, ce qui change, revers, « Projet vendoré : `/maj-workflow`.
  Décision : `docs/decisions/2026-10-06-suite-des-preuves-mods.md` (leçon 5) »).
- `WORKFLOW.md` : les deux lignes qui listent les exemptions du hook Stop (l.121 et la ligne
  `stop-contexte.mjs` du tableau des hooks, l.206) gagnent « session planifiée (rappel seulement) ».
