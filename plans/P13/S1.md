## T1 — Mod de fichiers et ses tests simulés

### Objectif
Écrire `preuves/mods/fichiers/`, un dossier de plugin autonome. Son module refuse un `tool.call`
`Edit`, `Write` ou `NotebookEdit` dont le fichier sort de la `Zone modifiée` de la session de plan
en cours, et laisse passer le reste. Ses tests `plugin test` le prouvent.

### Pourquoi
Aujourd'hui, la zone d'une session n'est qu'une consigne écrite : rien n'empêche une session
d'écrire ailleurs, et la disjonction des vagues parallèles repose sur la bonne foi. Si un mod la
garde, le parallèle devient sûr par construction. S5 installera ce module tel quel. S6 le mettra
ensuite à l'épreuve sur des sessions réelles.

### Décision clé
- Session retrouvée par l'`agentId` du `tool.call`, rattaché au lancement : `agent.spawn` dont le
  `prompt` nomme `plans/P<n>/S<k>.md`. La zone est la colonne 8 de la ligne `S<k>` de
  `plans/P<n>/index.md`, lue au moment du refus (pas de cache périmé).
- **Passent** : fil principal (sans `agentId`) ; sous-agent sans plan dans son prompt ; fichier
  dans la zone ; **fichiers de suivi du plan de la session**, `plans/P<n>/…` (le `S<k>.md`, l'index,
  `.echec.md`, `.revue.md`, `.verdict`, `.n0.json`) — sans ce cas, le mod refuserait à tort à
  chaque session son bilan et sa case `[x]` (critique de plan, constat 6) ; index illisible ou
  ligne introuvable (jamais un refus sur un doute).
- **Refusés** : hors zone ; zone `aucune` (sauf fichiers de suivi). Le motif nomme le fichier, la
  session et la zone, en une phrase lisible par la session refusée.
- Écritures par `Bash` (`>`, `>>`, `tee`, `sed -i`, `cp`, `mv`) : **comptées, pas refusées**.
- Chaque décision (refus, passage, `Bash` compté) s'ajoute en une ligne JSON à
  `<home>/.claude/preuves/mods/fichiers.jsonl` : horodatage, `agentId`, plan, session, outil,
  chemin, décision. Le chemin du dossier personnel n'est jamais écrit en dur.

### Référence
L'exemple `tool-call.ts` de la skill `plugin-authoring` (refus par `{ deny }`). Pour le format
d'un dossier de plugin testable, suivre la doc du kit.

### Lire / Modifier
- Lire : `plugin/bin/prochaine-action.mjs`
- Modifier : `preuves/mods/fichiers/` (créer) — manifeste du plugin, hooks.json qui nomme le module fichiers.ts, le module, ses tests et un index de fixture

### Étapes
1. Vérifier dans `types/claude-code.d.ts` les champs d'`agent.spawn` et de `tool.call` :
   `agentId`, un identifiant qui relie les deux, `prompt`. Si **rien ne relie** un `tool.call` à
   son `agent.spawn`, c'est le négatif de la décision : l'écrire au Bilan, livrer quand même le
   mod avec ce qui est possible, et le dire en `MOTIF`.
2. Écrire le module, puis les tests. Couvrir au minimum : hors zone (refus), zone (passe), fil
   principal (passe), zone `aucune` (refus), fichier de suivi `plans/P<n>/S<k>.md` (passe),
   sous-agent sans plan (passe), index illisible (passe), écriture `Bash` (comptée, passe).
   L'index utilisé par les tests est une fixture **dans** le dossier du mod.
3. Lancer la gate du mod (Validation) jusqu'au vert.
4. Bilan : ce que les types permettent ou non (relier `agentId` et session), cas non couverts.

### Validation
- **N0 auto (bloque le commit)** : gate du mod, depuis la racine : `"$CLAUDE_CODE_EXECPATH" plugin validate preuves/mods/fichiers/.claude-plugin/plugin.json` →
  `✔`, puis `"$CLAUDE_CODE_EXECPATH" plugin test preuves/mods/fichiers` → tous verts, puis
  `node tests/tester-hooks.mjs` → vert ; enfin `node plugin/bin/n0.mjs --session P13/S1` →
  PASS (sous verrou : preuve produite après stabilisation, l'orchestrateur la committe).
- **Tests** : les huit cas de l'étape 2, dans le dossier du mod.
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : `claude plugin validate` (le `claude` du PATH, ou sur un dossier) ne lit que
  le manifeste de marketplace et passe sur un module refusé par le moteur (P12, défaut 1). Seul
  `"$CLAUDE_CODE_EXECPATH" plugin validate <mod>/.claude-plugin/plugin.json` compte. Autre faux
  vert : des tests qui appellent la fonction de décision directement sans passer par le hook
  `tool.call` simulé du kit. Ils prouvent la logique, pas le refus.

### Si bloqué
Rien ici n'est irréversible ni public. Le négatif « l'`agentId` ne se relie pas à une session » est
un **résultat**, pas un arrêt : l'écrire, livrer, `VERDICT: PASS` si la gate est verte. Le kit de
test ou `$CLAUDE_CODE_EXECPATH` absents → `FAIL` environnement.
