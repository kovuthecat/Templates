## T7 — Les portes d'entrée renvoient à `/revue-d-usage`

### Objectif
Six textes nomment la nouvelle skill à l'endroit où l'utilisateur ou un modèle cherche la bonne
porte, et la règle N2 porte son exception écrite.

### Pourquoi
Une skill que rien n'aiguille ne se déclenche que si l'on connaît son nom. Et deux textes chargés à
chaque session (`CLAUDE-BASE.md`, `WORKFLOW.md` §6) disent aujourd'hui « Claude n'évalue pas le N2
— rien d'autre n'va dans `VALIDATION.md` ». Sans leur exception, la skill les contredit, et un
exécutant qui lit la règle générale refusera d'écrire les propositions.

### Décision clé
`docs/decisions/2026-09-23-revue-d-usage.md` : `/revue-d-usage` est une **étape de revue nommée, sans
rang** (même statut que `/code-review`, décision du 2026-08-30). **La grille s'arrête à trois.** N2
reste humain **par défaut**. L'exception tient en une phrase : *quand l'interview l'a demandé, Claude
propose sur le N2 — proposer, jamais trancher.* Une ligne par fichier, pas un paragraphe : chaque
fichier renvoie, le domicile de la règle est §6.

### Lire / Modifier
Modifier :
- `plugin/WORKFLOW.md` §6 ;
- `plugin/CLAUDE-BASE.md` (puce N2) ;
- `plugin/skills/verif-visuelle/SKILL.md` (« Point N2 à faire trancher ») ;
- `plugin/skills/revue-de-conception/SKILL.md` (table « La bonne porte », Étape 6) ;
- `plugin/templates/VALIDATION.md` (en-tête) ;
- `README.md` racine (table des skills, l. ~93-95).

Si le bilan de S1 a signalé un décompte ou une liste fermée d'agents, dans `plugin/README.md` ou
§5, l'ajouter au périmètre et y inscrire `parcoureur-usage`.

### Étapes
1. `WORKFLOW.md` §6, après le paragraphe « Desktop a un navigateur in-app… » : une puce ou une
   phrase, `/revue-d-usage` = étape de revue nommée sans rang, pas de N3, avec l'exception N2
   ci-dessus. `WORKFLOW.md` reste sous son plafond (300 lignes).
2. `CLAUDE-BASE.md` : dans la puce N2, une parenthèse qui renvoie à §6 (« sauf proposition demandée
   en `/revue-d-usage`, `WORKFLOW.md` §6 »). Pas une phrase de plus : ce fichier est payé à chaque
   session.
3. `verif-visuelle` : au paragraphe « Point N2 à faire trancher », une phrase. Pour une revue
   **d'ensemble** à un jalon (parcours, ergonomie, accessibilité), c'est `/revue-d-usage`. Cette
   skill-ci reste un N1 d'écran après une tâche.
4. `revue-de-conception` :
   - une ligne dans la table « La bonne porte » : « L'app telle qu'un utilisateur la vit (parcours,
     ergonomie, accessibilité) » → `/revue-d-usage` ;
   - Étape 6 : le `docs/decisions/` qu'elle écrit porte la ligne `Brief :` (gabarit
     `DECISIONS.md`, S2). Ici elle nomme les sections réécrites (Objectif, Hors périmètre), dans le
     même commit.
5. `templates/VALIDATION.md` : l'en-tête admet les **propositions issues d'une revue**
   (`/revue-d-usage`, passe esthétique demandée). Une par ligne `[ ]`, dans le bloc de son écran.
   Cochée, elle est acceptée et devient une tâche ; supprimée, elle est refusée. Le fichier reste
   « N2 uniquement » : une proposition est du N2.
6. `README.md` racine : une ligne de table pour `/revue-d-usage`, au format des voisines. Elle dit
   quand l'utiliser, ce qu'elle produit, et qu'elle ne corrige rien.

## T8 — Éval de déclenchement, cas positif et cas négatif

### Objectif
Deux cas dans `plugin/evals/`, lancés sur ce poste, avec le résultat écrit dans
`docs/analyses/2026-09-23-eval-revue-d-usage.md`.

### Pourquoi
La description de `/verif-visuelle` (« après une tâche qui change l'UI ») recouvre en partie celle de
la nouvelle skill. Un cas positif seul ne voit pas qu'elle capte les demandes de `/verif-visuelle`.
S4 ne publie que sur ce résultat écrit.

### Décision clé
Cas **positif** `revue-d-usage-jalon` : un prompt de jalon (« on arrive au MVP, fais une revue
d'usage de l'app : parcours, ergonomie, accessibilité »). Grader : `Skill` `revue-d-usage` `min: 1`.
Cas **négatif** `verif-visuelle-pas-revue-d-usage` : un prompt de fin de tâche UI (« j'ai fini la
tâche T3 de `plans/P1/S2.md` qui change l'écran de connexion, vérifie-le visuellement »). Graders :
`verif-visuelle` `min: 1` **et** `revue-d-usage` `min: 0` / `max: 0`.
Frontmatter des deux : `runs: 3`, `max_turns: 3`, `allowed_tools: [Read, Glob, Grep, Skill]`, sans
Bash (incident du 2026-09-17).
Seuil : positif `with` ≥ 2/3 et négatif `with` 3/3 sans `revue-d-usage`.

### Lire / Modifier
Créer : `plugin/evals/revue-d-usage-jalon/{prompt.md,graders/skill-invoquee.md}`,
`plugin/evals/verif-visuelle-pas-revue-d-usage/{prompt.md,graders/verif-visuelle-invoquee.md,graders/pas-revue-d-usage.md}`,
`docs/analyses/2026-09-23-eval-revue-d-usage.md`. Modifier seulement si le seuil n'est pas atteint :
la ligne `description` de `plugin/skills/revue-d-usage/SKILL.md` et/ou de
`plugin/skills/verif-visuelle/SKILL.md`.

### Étapes
1. Écrire les deux cas sur la forme des cas existants (regex `(?:[\w-]+:)?<skill>` pour tolérer le
   préfixe `workflow:`).
2. Lancer, au premier plan :
   `claude plugin eval plugin/ --trust-plugin --no-publish --max-cost-usd 3 --case revue-d-usage-jalon --case verif-visuelle-pas-revue-d-usage --json docs/analyses/evals-23.json`.
   Si `--case` ne se répète pas, deux lancements, un `--json` chacun.
3. Seuil atteint → écrire l'analyse (commande exacte, version de Claude Code, coût, table cas ×
   score `with`/`without`, verdict **PASS**).
4. Seuil manqué → reprendre la `description` fautive (une clause qui distingue : jalon et parcours
   pour l'une, écran après une tâche pour l'autre), relancer. **Deux tours au plus.** Au-delà,
   écrire l'analyse avec le verdict **FAIL** et les descriptions essayées, et rendre `FAIL`
   (`Nature : prémisse`, « la description ne sépare pas les deux skills »). S4 ne publie pas.
5. Commande introuvable ou refusée pour une raison de poste (version, bac à sable) → analyse avec le
   verdict **NON JOUÉE** et la sortie brute, `FAIL` avec `Nature : environnement`, et un incident
   `docs/workflow/incidents/2026-09-23-<slug>.md` (gabarit `WORKFLOW.md` §9b).
