## T11 — `rapatrier-git.mjs` : un `.git` déplacé revient dans son projet

### Objectif
Script `plugin/bin/rapatrier-git.mjs` :
- sans option, sur un dossier parent (`--projets <dossier>`, défaut : le parent de la racine du dépôt
  courant) : **liste** les projets dont `.git` est un fichier `gitdir: …`, avec la cible et sa taille ;
  ne modifie rien ;
- `--appliquer <projet>` (un projet par appel, ou `--tous`) : copie le dossier git pointé dans
  `<projet>/.git.rapatrie`, contrôle la copie, met le fichier `.git` de côté
  (`<projet>/.git.gitfile.bak`), renomme la copie en `.git`, puis vérifie : même `HEAD`, même
  `git status --porcelain`, `git fsck` sans erreur, `git worktree list` dont la première entrée est le
  dossier du projet. Échec d'un contrôle → retour exact à l'état d'avant (fichier `.git` remis), sortie
  non nulle, message.
- l'original dans `.gitdirs` n'est **jamais** supprimé ni modifié ; le script dit en fin de course quels
  dossiers de `.gitdirs` sont devenus des sauvegardes.

### Pourquoi
17 projets sur 38 ont leur `.git` déplacé dans `C:/Users/Kovu/.gitdirs/` (depuis le 2026-09-15).
L'outil `Agent` refuse d'y créer une copie isolée (« could not confirm that this repository's .git entry
belongs to the folder it is in »), et nos hooks refuseraient tout commit dans une telle copie
(`racineDepot` → `null`). L'utilisateur veut le parallèle sur **tous** ses projets et a choisi de
ramener les `.git` (2026-11-25). Fait à la main sur Templates le même jour : copie plutôt que
déplacement (le déplacement a été refusé : dossier hors zone ou verrouillé), contrôles identiques.

### Décision clé
- Copie puis bascule, jamais déplacement : le déplacement peut échouer à mi-course (refusé sur
  Templates) ; une copie ratée ne touche rien.
- Un projet dont un worktree lié existe déjà (`git worktree list` à plus d'une entrée) n'est **pas**
  rapatrié : ses chemins de worktree pointent vers l'ancien gitdir. Le script le liste à part, avec
  la raison.
- Aucune dépendance npm : Node + `git` seulement.

### Référence
Le geste fait sur Templates (décision, section « Constat ») : `cp -a <gitdir> .git.nouveau`, `mv .git
<bak>`, `mv .git.nouveau .git`, puis `git rev-parse HEAD`, empreinte de `git status --porcelain`,
`git worktree list`, `git fsck`.

### Lire / Modifier
- Modifier : `plugin/bin/rapatrier-git.mjs` (créer)
- Modifier : `tests/tester-scripts.mjs`

### Étapes
1. Écrire le script ; copie récursive par `fs.cpSync` (pas de `cp` shell : Windows).
2. Tests sur dépôts jetables créés dans le dossier temporaire du système par
   `git init --separate-git-dir <tmp>/gitdirs/x <tmp>/projets/x` (ce que sont les 17 projets) :
   (a) liste sans rien modifier ; (b) `--appliquer` → `.git` est un dossier, `HEAD`/status identiques,
   original intact ; (c) contrôle forcé en échec (ex. gitdir cible illisible) → état d'avant restauré ;
   (d) projet avec worktree lié → refusé avec la raison ; (e) projet déjà classique → ignoré.
3. Lancer le script **sans** `--appliquer` sur `C:/Users/Kovu/Projets` et recopier la liste au bilan
   (nombre attendu : 16, Templates étant déjà fait) — c'est la liste que l'utilisateur appliquera.
