## T15 — Lecture de `Parallèle :` et décision de lancer en parallèle

### Objectif
- `lire-index.mjs` lit la ligne d'en-tête `Parallèle : oui | non` (absente = `non`) ; copie des mods
  régénérée par le mécanisme existant.
- Plan `Parallèle : oui` : l'action `lancer` rend **toutes** les sessions lançables de la vague (au lieu
  d'une), chaque appel d'agent portant `isolation: "worktree"`, sans plafond.
- Le moteur rend un `lancer` **en série** (une session), avec le motif dans le texte de l'annonce, quand :
  (a) deux sessions lançables de la vague ont des zones qui se recoupent (préfixe de chemin commun dans
  la colonne Zone modifiée) ; (b) le dépôt n'a pas de dossier `.git` à sa racine (`.git` fichier) — motif :
  « lance `node <…>/rapatrier-git.mjs --appliquer <projet>` » ; (c) `racineIntrouvable`.
- `verifier-plan.mjs` signale dès la rédaction une vague d'un plan `Parallèle : oui` dont deux zones se
  recoupent (avertissement, pas un écart : le moteur sait la passer en série).

### Pourquoi
C'est la demande de l'utilisateur : qu'une vague de quatre sessions dure le temps de la plus longue. Les
cas (a)-(c) sont ceux où des copies parallèles casseraient : fusion de fichiers communs, outil `Agent`
qui refuse la copie (cadrage de P21), hooks qui refusent les commits.

### Étapes
1. `lire-index` : champ `parallele: boolean`.
2. `decider` : branche `parallele` qui rassemble les sessions lançables de la vague ; cas (a)-(c) →
   une seule, motif dans l'action (`motifSerie`) et dans `texte`.
3. Prompt de session rendu en mode parallèle : « tu travailles dans une copie isolée ; ne coche pas
   l'index, ne touche ni `STATUS.md` ni `TASKS.md` : le moteur le fait à la collecte » — c'est ce qui
   évite les conflits de fusion sur les lignes voisines de l'index (critique, constat 2 ; sonde M2). Le

4. Fixtures : plan `Parallèle : oui` à vague de trois sessions disjointes → un `lancer` à trois appels ;
   zones recoupées → série + motif ; `.git` fichier → série + motif ; plan sans ligne → identique à 0.68.0.

## T16 — État d'une vague en vol, collecte par fusion, reprise après coupure

### Objectif
- **État durable « en cours »** : à chaque lancement parallèle, l'orchestrateur rappelle le moteur avec
  `--lancee S<k> --agent <id>` ; le moteur l'inscrit dans `.claude/vague-en-cours.json` (non suivi :
  plan, vague, session → agent, branche `worktree-agent-<id>`, heure). Une session inscrite est
  `en-cours` : jamais relancée par un rappel du moteur pendant que les autres tournent (critique,
  constat 3). La branche se retrouve aussi par `git worktree list` si le fichier manque.
- **Collecte** : `--collecter S<k>` (à chaque verdict, quel qu'il soit) fusionne la branche de la session
  dans `main` par `git merge --no-ff` avec un message **sans** ligne `Plan:` à barre finale (format fixé
  par la sonde M1, par défaut `Fusion P<n>/S<k>`), puis `git worktree remove` et suppression de la
  branche, puis désinscription. Une branche `FAIL` ou `QUESTION` est fusionnée aussi : son `.echec.md` /
  `.question.md` arrive ainsi dans `main`, où le moteur le lit. Conflit → `git merge --abort`, copie et
  branche conservées, `question` source `fusion-conflit` (options : résoudre à la main puis relancer ;
  relancer la session en série sur `main`).
- **Coupure** : `--interruption S<k>` sur une session inscrite fusionne d'abord ce que porte sa branche
  (commits partiels), puis rend `relancer-interrompue`, sans consommer de reprise ; une coupure par
  quota de toute la vague se traite session par session, de la même façon.
- Coche, revue, preuve et push : inchangés, après fusion (le moteur coche déjà, l.~2137).

### Pourquoi
Sans état durable, un rappel du moteur après le premier verdict relancerait les sessions encore en vol
dans une seconde copie ; sans fusion de toutes les branches, un `FAIL` ou une question resterait
invisible ; sans message de fusion contrôlé, la preuve N0 deviendrait illisible (critique, constat 6).

### Décision clé
- Fusion, jamais `rebase` (décision : la preuve est calculée sur le commit de la session).
- Conflit de fusion : jamais résolu par le moteur ni par l'orchestrateur — toujours une question.
- `.claude/vague-en-cours.json` est supprimé quand la vague n'a plus de session inscrite ; la clôture
  du plan refuse s'il en reste (motif explicite).

### Lire / Modifier
- Modifier : `plugin/bin/prochaine-action.mjs`
- Modifier : `tests/tester-scripts.mjs`
- Modifier : `tests/scenarios/` (scénario de vague parallèle)
- Modifier : `tests/fixtures/plans/` (créer les fixtures nécessaires)
- Modifier : `tests/fixtures/scenarios/` (créer les fixtures nécessaires)

### Étapes
1. Inscription / désinscription, état `en-cours` dans `assembler`.
2. `--collecter` : fusion, nettoyage, conflit → question.
3. `--interruption` sur session inscrite.
4. Scénario « vague parallèle à deux sessions » joué avec de **vrais** worktrees (`git worktree add`)
   dans un dépôt de fixture, chaque session factice écrivant comme une vraie (commits de tâche, preuve
   N0, et **pas** d'écriture de l'index) : premier verdict → l'autre n'est pas relancée ; les deux
   collectées → deux lignes cochées à la même collecte, preuves valides après fusion (`valider-n0` ne
   boucle pas). Variantes : conflit → question ; coupure → fusion partielle + `relancer-interrompue`.
