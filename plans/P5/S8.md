## T26 — Trois cas dans `plugin/evals/`

### Objectif
`plugin/evals/<cas>/prompt.md` + `graders/*.md` pour : `fin-de-tache` déclenchée sur une fin de
session de plan ; `orchestrer-plan` déclenchée sur « lance la vague 2 » ; aucune des deux (ni
`cadrer`, ni `nouveau-plan`) sur une correction de coquille.

### Pourquoi
B5 : « feu rouge avant publication au lieu d'un incident après » ; signal d'entrée atteint (16
publications correctives en 22 jours). Les deux skills les plus corrigées sont les deux testées.
Le cas négatif est ce qui protège la voie courte : une skill qui se déclenche sur une coquille
coûte un contexte pour rien.

### Décision clé
Décision (g). Trois cas, dans cette forme (à ajuster aux champs exacts lus dans la doc) :

- `fin-de-tache-fin-de-session/prompt.md` — frontmatter `runs: 3`, `max_turns: 3`,
  `allowed_tools: [Read, Glob, Grep, Skill]` ; corps : « J'ai terminé les tâches de
  `plans/P1/S2.md`, N0 est vert, tout est prêt à committer. Clos la session. »
  `graders/skill-invoquee.md` : `type: tool_used`, `tool: Skill`, `input_match:
  '"skill"\s*:\s*"(?:[\w-]+:)?fin-de-tache"'`.
- `orchestrer-plan-lancer-vague/prompt.md` — même frontmatter ; corps : « Lance la vague 2 du plan
  P3. » Grader identique sur `orchestrer-plan`.
- `coquille-sans-skill/prompt.md` — même frontmatter ; corps : « Corrige la coquille « recieve » →
  « receive » dans `README.md`. » Quatre graders `tool_used` sur `Skill`, `min: 0`, `max: 0`, un par
  skill : `fin-de-tache`, `orchestrer-plan`, `cadrer`, `nouveau-plan`.

Le bac à sable ne charge que le plugin : les fichiers cités par les prompts n'existent pas, et
c'est voulu — on teste le **déclenchement**, pas l'exécution ; `max_turns: 3` borne ce que la
session peut faire après.

### Lire / Modifier
- Créer : `plugin/evals/fin-de-tache-fin-de-session/`, `plugin/evals/orchestrer-plan-lancer-vague/`,
  `plugin/evals/coquille-sans-skill/` (chacun `prompt.md` + `graders/`).

### Étapes
1. Lire les champs exacts (via `lecteur-doc`) ; écrire les trois cas.
2. `claude plugin eval plugin/ --trust-plugin --runs 1 --no-publish --max-cost-usd 3 --json
   /tmp/evals-essai.json` — un run d'essai pour valider le format (pas le résultat).
3. Corriger le format si la commande refuse un champ ; ne pas toucher au sens des cas.

### Validation
- **N0 auto (bloque le commit)** : la commande de l'étape 2 sort `0` ou `1` (cas chargés, verdict
  rendu), **jamais** une erreur de chargement de cas ; `ls plugin/evals/*/graders/*.md | wc -l` → `6`.
- **Tests** : —
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : un cas positif dont le prompt **nomme** la skill (« lance /fin-de-tache ») —
  il teste l'obéissance, pas le déclenchement. Aucun prompt ne contient un nom de skill.

### Si bloqué

## T27 — Lancer, consigner

### Objectif
Un run complet (3 runs par cas, bras témoin par défaut), plafonné, et une analyse courte qui dit ce
que chaque cas a rendu, ce que ça coûte, et ce qui en découle.

### Pourquoi
Un résultat d'éval qui n'est pas écrit sera relancé. Et la première mesure est la référence des
suivantes (rapport §8.2 : figer le corpus et l'état avant de modifier le workflow).

### Décision clé
Analyse dans `docs/analyses/2026-09-<jj>-evals-premiere-passe.md`, forme des analyses existantes :
statut, version de Claude Code, commit, commande exacte, coût affiché, table cas × verdict (avec /
sans plugin), et **une** conclusion par cas : tient · ne tient pas · ambigu. Un cas qui ne tient pas
n'est pas corrigé ici : il devient une entrée pour `/cadrer` ou `/analyser-incidents`.

### Lire / Modifier
- Créer : `docs/analyses/2026-09-<jj>-evals-premiere-passe.md`.

### Étapes

2. Écrire l'analyse depuis le JSON : `costUsd`, `casesPassed`, verdict par cas, `partialReason`
   s'il est présent (plafond de coût atteint = résultat partiel, à dire).
3. Relier à B5 dans l'analyse du 2026-09-12 : une ligne `Statut : première passe faite <date>,
