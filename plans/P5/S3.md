## T7 — Trois assertions de plus dans `tester-renvois.mjs`

### Objectif
Assertions 4, 5 et 6, dans le moule des trois existantes, `exit 1` si l'une échoue.

### Pourquoi
Un renvoi présent peut désigner un agent absent ; un frontmatter dont une valeur contient `: ` non
citée tombe **en entier et en silence** (Trail of Bits) ; une annexe citée par une autre skill
échappe aux assertions 2 et 3, qui ne regardent que la skill propriétaire. Trois trous, trois
contrôles déterministes.

### Décision clé
Décision (g). Les trois contrats, et rien d'autre :

4. **Agent cité = agent présent.** Pour tout fichier texte de `plugin/**` : chaque
   `subagent_type: "<x>"` où `<x>` n'est pas un agent natif (`general-purpose`, `Explore`, `Plan`,
   `claude-code-guide`, `statusline-setup`, `claude`) doit correspondre à `plugin/agents/<x>.md`.
   Même contrôle sur les noms de la liste de `WORKFLOW.md` §5 (`` `<x>` → `` en début de puce).
5. **Frontmatter sain.** Pour chaque `plugin/skills/*/SKILL.md` et `plugin/agents/*.md` : le bloc
   `---…---` de tête existe ; chaque ligne est `clé: valeur` ; `name` est en kebab-case ; une skill
   n'a pas de clé `tools`, un agent n'a pas de clé `allowed-tools` ; aucune valeur non citée ne
   contient `: ` ni ` #`. Parseur maison ligne à ligne, pas de bibliothèque YAML.
6. **Citation croisée résolue, annexe sans chaîne.** Toute occurrence de
   `${CLAUDE_PLUGIN_ROOT}/skills/<s>/references/<x>.md` dans `plugin/**` pointe un fichier existant ;
   aucun `plugin/skills/*/references/*.md` ne contient lui-même une citation `references/<y>.md`
   (une annexe ne chaîne pas — Trail of Bits, « one level deep »).

### Référence
`tests/tester-renvois.mjs` l. 147-200 — les assertions 2 et 3 : même forme de message d'écart
(`plugin/…:ligne — ce qui est déclaré — ce que le dépôt dit`), même compte affiché après exécution.

### Lire / Modifier
- Modifier : `tests/tester-renvois.mjs`.

### Étapes
1. Écrire l'assertion 4 ; la faire tourner ; sur l'arbre actuel elle doit être **verte** (les sept
   agents cités existent). Vérifier le rouge en local en renommant temporairement un
   `subagent_type` dans une copie mentale — **sans commit** — puis remettre.
2. Écrire l'assertion 5 ; verte sur l'arbre actuel. Si elle sort rouge : lire quelle valeur contient
   `: ` ; si c'est vrai, c'est un résultat (bilan), pas une correction ici.
3. Écrire l'assertion 6 ; sur l'arbre actuel il n'existe aucune citation croisée : l'assertion doit
   le dire (`(0 citation(s) croisée(s) inspectée(s))`) et rester verte, **sans** déclarer « motif
   cassé » — contrairement aux assertions 2 et 3, zéro est ici un état normal jusqu'à S4.
4. Mettre à jour le commentaire d'en-tête du fichier (« Trois assertions » → « Six assertions »).

### Validation

  `Tous les cas sont OK.`, `exit 0` ; `node plugin/bin/publier.mjs --dry-run` → passe (il appelle
  ce test).
- **Tests** : mutation à la main, non commitée, pour chaque assertion : (4) un `subagent_type:
  "inexistant"` ajouté dans une copie de `remediation.md` → rouge ; (5) un `description: a: b` →
  rouge ; (6) une citation `${CLAUDE_PLUGIN_ROOT}/skills/cadrer/references/absent.md` → rouge.

## T8 — `stop-contexte` : marqueur de session non inscriptible

### Objectif
Un cas de `tester-hooks.mjs` où le chemin du marqueur de session n'est pas inscriptible, et qui
vérifie que le hook rend un résultat borné (bloque une fois puis rappelle sans bloquer, ou laisse
passer avec un message) — jamais une erreur non gérée, jamais un blocage répété.

### Pourquoi
D6 : le hook choisit un blocage initial puis des rappels, avec un marqueur de session. « Il faut
tester ce mécanisme, notamment si le marqueur ne peut pas être écrit. » Sans ce cas, le seul
anti-boucle du hook Stop n'est pas couvert.

### Décision clé
Le comportement attendu est **celui que le code a aujourd'hui** face à cette panne, s'il est borné.
S'il ne l'est pas (exception, blocage à chaque Stop), c'est un `FAIL` de nature `prémisse` : le
plan supposait le hook borné. On ne corrige pas le hook ici.

### Lire / Modifier
- Modifier : `tests/tester-hooks.mjs`.

### Étapes
1. Lire dans `stop-contexte.mjs` où le marqueur est écrit et comment l'échec d'écriture est traité.
2. Écrire le cas : dépôt temporaire avec code modifié sans fichier de suivi (comme le cas l. 123),
   marqueur rendu non inscriptible (répertoire à la place du fichier, ou chemin sous un fichier
   ordinaire — choisir ce qui marche sous Windows **et** Linux ; ne pas se reposer sur `chmod`).
3. Assertion : le hook sort sans exception ; deux appels successifs ne rendent pas deux blocages
   identiques, ou le premier explique qu'il ne peut pas poser son marqueur.

### Validation
- **N0 auto (bloque le commit)** : `node tests/tester-hooks.mjs` → 24 cas, `Tous les cas sont OK.`
- **Tests** : le cas ci-dessus.
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : un cas qui affirme « sort sans erreur » en avalant l'exception dans le test
  lui-même. Le hook doit sortir proprement, pas le test.

### Si bloqué
Le hook n'a aucun traitement de l'échec d'écriture et lève → `FAIL`, nature `prémisse`, ligne « Ce
qu'il faudrait pour que ça passe » : « `stop-contexte.mjs` doit tolérer un marqueur non
inscriptible ; à corriger dans une session dédiée à `plugin/hooks/` ».

### Message de commit
`test(hooks): stop-contexte avec marqueur non inscriptible`
Dernière ligne : `Plan: P5/S3/T8`
