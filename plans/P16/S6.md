## T10 — Panneau « plan » : vague, sessions, prochaine action, boutons

### Objectif
Un panneau `plan` : plan et vague en cours, statut de chaque session de l'index, prochaine action
(texte de `prochaine-action.mjs`), et quatre boutons de relance.

### Pourquoi
Piloter l'orchestration en un appui, y compris depuis le téléphone où seul le panneau est rendu
(brief MVP 3) : les relances tapées à la main sont ce que le brief veut réduire.

### Décision clé
- Données : `prochaine-action.mjs P<n> --json` (action, vague, sessions, `avertissement`) et
  `--etat --json` (statuts) — le cache 20 s de S5 est partagé. Pas de plan en cours → panneau absent.
- **Boutons** (`$.prompt.submit({ text })`) — préfixe de skill selon le mode : vendoré `/<skill>`,
  dépôt source `/workflow:<skill>` (même détection que `installer-mods.mjs`) :
  | Bouton | Texte soumis |
  | --- | --- |
  | Go | `Go` |
  | Reprends | `/reprendre` |
  | Enchaîne l'orchestration | `/orchestrer-plan P<n>` |
  | Commit+push | `Committe et pousse le travail en attente, selon /fin-de-tache.` |
- Un bouton pressé pendant un tour en cours est mis en file par le moteur (`$.prompt.submit`) ; pas
  de logique propre.

## T11 — Commande `/incidents` : les incidents de tous les projets

### Objectif
`/incidents` liste les incidents de workflow de tous les projets frères (`<parent de la racine>/*/docs/workflow/incidents/*.md`),
du plus récent au plus ancien : projet · date · titre · nature.

### Pourquoi
Rassembler sans script ni changement de projet ce que `/analyser-incidents` traite depuis Templates
(brief MVP 4) ; un incident vu dans trois projets est un défaut du workflow.

### Décision clé
- Logique d'en-tête **portée** de `plugin/bin/collecter-incidents.mjs` (lecture des champs, incident
  non conforme listé quand même, champs vides) — le mod n'a pas Node : `$.fs.list` / `$.fs.read`.
  Option `/incidents <YYYY-MM-DD>` = « depuis ». Pas de `fetch`, pas d'écriture.
- Silencieuse hors projet du workflow (pas de `.claude/workflow/manifest.json` ni de
  `plugin/.claude-plugin/plugin.json`) : la commande n'est pas enregistrée.
- Sortie `{ text }` en table markdown, 50 lignes au plus, puis « … et <n> autres ».

### Lire / Modifier
- Lire : `plugin/bin/collecter-incidents.mjs` — parsing des en-têtes
- Lire : `plugin/WORKFLOW.md` — §9b (gabarit d'incident)

- Modifier : `plugin/mods/affichage/hooks/register.tsx`
- Modifier : `plugin/mods/affichage/tests/incidents.test.ts` (créer)

### Étapes
1. Parsing pur (`incidents.ts`), tests sur deux incidents réels de `docs/workflow/incidents/` recopiés

2. Commande ; test de `command.run` avec `fs` simulé (deux projets, un sans dossier d'incidents).
3. `validate`, `test` ; N0 ; commit T11.

### Validation
