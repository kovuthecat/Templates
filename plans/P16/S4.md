## T6 — Publier 0.56.0 avec garde-fous

### Objectif
Bump `0.56.0` (plugin `workflow` et `garde-fous`), ligne de CHANGELOG, commit, `publier.mjs` ; le
poste rend `workflow@templates` et `garde-fous@templates` enabled à 0.56.0.

### Pourquoi
Les projets vendorés ne reçoivent les mods que par une version publiée ; et Templates ne charge
`garde-fous` qu'une fois installé, ce que `publier.mjs` fait désormais (S2).

### Décision clé
- **Premier geste** : `"$CLAUDE_CODE_EXECPATH" auth status`. Session OAuth expirée → `FAIL`
  environnement, geste humain : `claude auth login` (constat 7 du critique ; K l'a rencontré).
- CHANGELOG, forme des entrées existantes : **Mods du workflow : garde-fous** — ce que ça change
  (O1 filet de modèle, O3 premier plan par défaut, installation par `/maj-workflow`), revers (chaque
  changement de mod = nouvelle version ; échec d'installation signalé, non bloquant), « Projet
  vendoré : `/maj-workflow` », décisions `2026-10-06-apres-p15.md`.
- Sortie 3 de `publier.mjs` : lancer à la main la commande qu'il affiche, puis la relancer ; tout
  écart persistant se consigne dans la preuve, avec le binaire utilisé.

### Lire / Modifier

- Modifier : `plugin/mods/garde-fous/.claude-plugin/plugin.json`
- Modifier : `CHANGELOG.md`

2. Bump des deux `plugin.json`, CHANGELOG ; N0 (`tester-mods` vérifie l'alignement) ; commit ; push.

## T7 — Preuve : les garde-fous agissent dans un projet vendoré, et pas sans eux

### Objectif
Écrire `docs/analyses/2026-10-06-mods-distribution-preuve.md` : installation dans un projet vendoré
de test, effet O1 observé avec les mods, absent sans eux.

### Pourquoi
Seule une exécution tranche le premier risque du plan : un `plugin list` « enabled » ne prouve pas
qu'un module est chargé (un module refusé se tait, P12), et un agent au bon modèle ne prouve rien si
`model` était déjà fourni (constat 5 du critique).

### Décision clé
- **Fixture** dans le scratchpad (jamais commitée) : dossier `p16-fixture`, `git init`, vendoré par
  `sync-workflow.mjs` depuis le cache 0.56.0, comme le font les cas de `tests/tester-scripts.mjs` ;
  `plans/P1/index.md` (forme du squelette, S1 en **Haiku**) et `plans/P1/S1.md` trivial.
- `node .claude/workflow/bin/installer-mods.mjs` (dans la fixture) → 0 ; citer le nom de marketplace
  généré et le bloc de `plugin list`.
- **Sonde positive** : depuis la fixture, `"$CLAUDE_CODE_EXECPATH" -p --model sonnet` avec
  `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, consigne : lancer l'outil `Agent`, `subagent_type:
  general-purpose`, **sans** paramètre `model`, prompt « Lis plans/P1/S1.md et réponds OK ». Relever
  le modèle de la première réponse du sous-agent dans sa transcription (`~/.claude/projects/…`) →
  attendu : Haiku. Vérifier aussi que la session principale est bien en Sonnet.
- **Témoin négatif** : `plugin disable garde-fous@<mkt> --scope local`, même sonde → attendu : le
  modèle de la session (Sonnet). Puis `enable`.
- **Remise en ordre** : désinstaller les mods de la fixture, `marketplace remove` de sa marketplace,
  supprimer la fixture ; `known_marketplaces.json` ne garde que ses entrées d'avant (citer).
- Fichier de preuve : une section par mesure (commande qui reproduit, lignes citées, verdict contre
  le critère ci-dessus), binaire qui a installé, puis « Réfuté » / « Reste ouvert » (O3 n'est prouvé
  que par ses tests et P13 : à écrire tel quel).
- Sonde positive négative (Sonnet avec les mods) → `FAIL` nature `prémisse`, affirmation falsifiable :
  « un module installé --scope local depuis .claude/workflow/mods n'est pas chargé par une session -p ».
