## T4 — `/maj-workflow` et `/migrer-projet` installent les mods

### Objectif
Les deux skills lancent `node .claude/workflow/bin/installer-mods.mjs` et tolèrent dans
`.claude/settings.local.json` les entrées de la marketplace des mods ; la doc du dépôt source suit.

### Pourquoi
C'est ce qui rend vraie la promesse « rien à installer à la main, sur aucun poste » : un poste neuf
qui clone un projet à jour n'a rien à synchroniser, mais rien d'installé.

### Décision clé
- **`/maj-workflow`** : nouvelle étape après la synchro (avant la vérification), lancée **toujours**,
  même si `--check` n'avait rien à faire. Sortie 0 → une ligne au rapport ; 3 → **signalé, non
  bloquant** : la synchro se commite, le rapport cite la commande à relancer ; 4 (sans CLI) → une
  ligne « mods non installés : pas de CLI Claude Code sur ce poste », rien d'autre. La phrase
  « sans plugin, sans marketplace, sans rien installer » (l.12-13) est corrigée : le workflow vendoré
  reste sans plugin ; seuls les mods s'installent, localement au poste.
- **Exception aux interdits** (`maj-workflow` l.105-107, `migrer-projet` Phase A et D3) : des entrées
  `enabledPlugins` / `extraKnownMarketplaces` **dans `.claude/settings.local.json`**, pour une
  marketplace `workflow-mods-*`, sont attendues ; les mêmes dans `settings.json`, ou pour
  `workflow@…`, restent un résidu de double chargement. Pourquoi : la marketplace des mods est propre
  au poste (nom haché sur le chemin), jamais commitable.
- **`/migrer-projet`** : même appel après D2 (synchro propre), même conduite sur 3 et 4 ; D5 (session
  neuve) vérifie par `installer-mods.mjs --verifier`.
- **Dépôt source** : `nouveau-plan/SKILL.md` Étape 0 (dépôt source → `claude plugin update
  workflow@templates --scope local`) ajoute `node plugin/bin/installer-mods.mjs` ;
  `fin-de-tache/references/fin-de-plan.md` 8b : le bump porte aussi sur le `plugin.json` de chaque
  mod (N0 `tester-mods` le refuse sinon), et `publier.mjs` installe les mods ; `CLAUDE.md` (« Règles
  spécifiques ») : une phrase — poste neuf : `node plugin/bin/installer-mods.mjs` après l'installation
  du plugin `workflow`.

## T5 — SessionStart signale des mods absents ou en retard

### Objectif
`sessionstart-contexte.mjs` ajoute une ligne quand un mod du projet n'est pas installé `--scope
local` pour ce dossier à la version attendue, avec la commande à lancer ; muet en session cloud.

### Pourquoi
Le choix « échec signalé, non bloquant » n'est sûr que si le signal revient à chaque session ; c'est
aussi le seul filet du poste neuf qui n'a pas encore passé de frontière de plan.

### Décision clé
- Lecture seule, **sans lancer de processus** (budget du hook) :
  `<CLAUDE_CONFIG_DIR ou ~/.claude>/plugins/installed_plugins.json`. Mods attendus = sous-dossiers de
  `.claude/workflow/mods/` (vendoré) ou `plugin/mods/` (source) portant `.claude-plugin/plugin.json` ;
  pour chacun, une entrée `<mod>@<mkt quelconque>` `scope: local`, `projectPath` = racine (chemins
  normalisés), `version` = attendue.
- Écart → ligne : `**Mods non installés ou en retard** (<liste>) — \`node .claude/workflow/bin/installer-mods.mjs\``
  (source : `node plugin/bin/installer-mods.mjs`).
- Muet si `CLAUDE_CODE_REMOTE` vaut `true` (session cloud), si aucun mod n'est présent, ou sur toute
  erreur de lecture (pas de faux positif, comme les contrôles voisins l.180-219).

### Lire / Modifier
- Lire : `plugin/hooks/sessionstart-contexte.mjs` — l.150-219 (contrôles de version voisins, racineDepot)
- Modifier : `plugin/hooks/sessionstart-contexte.mjs`
- Modifier : `tests/tester-hooks.mjs`

### Étapes
1. Le contrôle, dans le style des blocs voisins (commentaire « pourquoi » daté).
2. Tests (`CLAUDE_CONFIG_DIR` jetable) : mod absent → ligne ; version en retard → ligne ; tout en
   place → silence ; `CLAUDE_CODE_REMOTE=true` → silence ; JSON illisible → silence ; installé pour
   un **autre** `projectPath` → ligne.
3. N0, commit T5.
