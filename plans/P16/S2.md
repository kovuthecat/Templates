## T2 — `installer-mods.mjs` : installe et vérifie les mods du poste, idempotent

### Objectif
Un script `plugin/bin/installer-mods.mjs` (vendoré avec le reste de `bin/`) qui, lancé depuis la
racine d'un projet, installe ou met à jour `--scope local` chaque mod présent, puis vérifie qu'ils
sont enabled à la bonne version ; la marketplace `templates` gagne l'entrée `garde-fous`.

### Pourquoi
« Rien à installer à la main » (décision `apres-p15`) exige un geste unique et rejouable, appelé par
`/maj-workflow`, `/migrer-projet` et `publier.mjs` : en prose dans trois skills, il divergerait.

### Décision clé
- **Deux modes, détectés** : *vendoré* (`.claude/workflow/manifest.json` présent) → mods dans
  `.claude/workflow/mods/` ; *source* (pas de manifeste, `plugin/.claude-plugin/plugin.json` présent)
  → mods dans `plugin/mods/`, marketplace `templates` existante. Ni l'un ni l'autre → sortie 1.
- **Mods = sous-dossiers de `mods/` portant `.claude-plugin/plugin.json`** (liste dynamique : affichage
  s'y ajoutera en S5 sans retoucher le script). Version attendue = celle de chaque `plugin.json`.
- **Marketplace en mode vendoré, générée par le script** (constat 4 du critique) :
  `.claude/workflow/mods/.claude-plugin/marketplace.json` = `{ name, owner, plugins: [{ name, source:
  "./<mod>" }] }`, nom `workflow-mods-<slug du nom de dossier du projet>-<6 premiers hex du sha256 du
  chemin absolu normalisé>` — unique par poste et par dossier, car `known_marketplaces.json` est global
  et n'a qu'un chemin par nom. Ce fichier est **ignoré par git** (`plugin/mods/.gitignore` vendoré :
  `/.claude-plugin/`, **ancré** — sans la barre initiale il ignorerait aussi le `plugin.json` de
  chaque mod ; vérifier par `git check-ignore`) et hors manifeste : il dépend du poste.
- **Binaire** (constat 1) : `process.env.CLAUDE_CODE_EXECPATH` s'il est défini, sinon `claude` (via
  shell sous Windows, comme `publier.mjs:212-217`). Le binaire utilisé est imprimé.
- **Séquence** : lire `<CLAUDE_CONFIG_DIR ou ~/.claude>/plugins/known_marketplaces.json` → nom absent :
  `plugin marketplace add <dossier mods> --scope local` ; nom présent avec un autre `installLocation`
  (comparaison de chemins normalisés, casse ignorée sous Windows) : `plugin marketplace remove <nom>`
  puis `add`. (Mode source : la marketplace `templates` doit exister ; absente → sortie 3 avec la
  commande de `CLAUDE.md`.) Puis pour chaque mod, d'après `installed_plugins.json` (entrée
  `scope: local` dont `projectPath` = racine) : absent → `plugin install <mod>@<mkt> --scope local` ;
  version ≠ attendue → `plugin update <mod>@<mkt> --scope local`. Enfin vérification par
  `plugin list` : bloc `<mod>@<mkt>` avec `Version: <attendue>` et `enabled` (même lecture que
  `publier.mjs:235-242`, factoriser si simple).
- **Sorties** : 0 tout installé et vérifié ; 1 usage / racine non reconnue ; 3 installation ou
  vérification en échec (message + commande à relancer) ; 4 aucun binaire lançable (ENOENT) — « sans
  CLI », que les skills traiteront comme un signal, pas une erreur (S3). Option `--verifier` : aucun
  changement, 0 si tout est en place, 3 sinon.
- **Marketplace `templates`** : ajouter `{ "name": "garde-fous", "source": "./mods/garde-fous" }` à
  `plugin/.claude-plugin/marketplace.json`.

## T3 — Vendoring des mods, publication gardée, contrôle des mods en N0

### Objectif
`sync-workflow.mjs` vendore `mods/` dans `.claude/workflow/mods/` ; un nouveau `tests/tester-mods.mjs`
valide et teste chaque mod et vérifie l'alignement des versions ; `.claude/n0.json` le lance ;
`publier.mjs` l'exige avant publication et installe les mods après la mise à jour du plugin local.

### Pourquoi
Un module invalide se tait au chargement (P12) : sans gate, `affichage` pourrait être publié cassé
et « enabled » (constat 2). Une version de mod non bumpée n'est jamais rechargée (P12).

### Décision clé
- **sync** : entrée `PLAN` `mods` → `.claude/workflow/mods/`, **sans substitution** de
  `${CLAUDE_PLUGIN_ROOT}` (drapeau à ajouter, ex. `brut: true`) et **sans** le `sauf: ['hooks.json']`
  (le `hooks.json` d'un mod est son module). Les fichiers entrent au manifeste (DÉRIVE comprise), sauf
  le `.claude-plugin/marketplace.json` généré (il n'existe pas en source : rien à exclure, vérifier
  seulement qu'il n'est pas supprimé comme obsolète).
- **`tests/tester-mods.mjs`** : pour chaque `plugin/mods/<mod>/` portant `.claude-plugin/plugin.json` :
  version == `plugin/.claude-plugin/plugin.json` ; entrée présente dans
  `plugin/.claude-plugin/marketplace.json` ; `<bin> plugin validate <mod>/.claude-plugin/plugin.json`
  et `<bin> plugin test <mod>` à 0. `<bin>` = `CLAUDE_CODE_EXECPATH`, sinon `claude` ; aucun binaire →
  échec nommé, **jamais un saut silencieux**. Sortie 1 au moindre écart.
- `.claude/n0.json` : ajouter `{ "nom": "tester-mods", "cmd": "node tests/tester-mods.mjs" }`.
- **`publier.mjs`** : hors `--dry-run`, lance `tester-mods.mjs` avec les autres pré-contrôles (refus
  sinon) — en `--dry-run` la N0 l'a déjà lancé ; après `mettreAJourPluginLocal()`, lance
  `installer-mods.mjs` (mode source) ; échec → sortie 3, comme le plugin local, avec la commande à
  relancer. En-tête (l.19, sorties) mis à jour.
