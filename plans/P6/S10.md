## T23 — De l'état à l'action

### Objectif
`node plugin/bin/prochaine-action.mjs P<n> [--json]` rend **une** action parmi celles de C2.

### Pourquoi
Budget, table nature → modèle, dépendances et recoupement par les commits sont déterministes ; les
faire suivre en prose par un modèle est la première source d'erreurs d'aiguillage, payées en
sessions Opus.

### Décision clé
Les tables de `remediation.md` se reprennent **telles quelles** — ce n'est pas le moment de les
améliorer. Ordre d'évaluation : `wave.lock` présent → `question` · vague close non poussée →
`pousser` · session en échec de la vague courante → cycle de remédiation (budget d'abord) · vague
close sans revue → `relire` · `validation-humaine` · vague suivante → `lancer` · sinon `fini`.
`regler-effort` n'est rendu qu'une fois : aucun commit `Plan: P<n>/` n'existe encore.

### Lire / Modifier
`plugin/bin/prochaine-action.mjs`, `tests/tester-scripts.mjs`, `tests/fixtures/plans/`.

### Étapes
1. Moteur sur l'état de `--etat`, dans l'ordre ci-dessus.
2. Remédiation : `prémisse` sans `Mesure` → `verifier-premisse` ; avec `Mesure` (commit vérifié par
   `git cat-file -e`) → `question` ; `environnement` → `reprendre` même modèle ; `exécution` →
   un cran au-dessus, plancher Sonnet ; session Opus → `enqueter`, sauf `Blocage :` qui nomme un
   geste → `reprendre` même modèle ; `Auto : oui · option <m>` → `reprendre` avec l'option ;
   budget session (2 reprises, 1 enquête) ou plan (2 enquêtes) épuisé → `question` ;
   `reprise-manuelle` → `question`.
3. `question` porte `motif` et `options` = la **source** des options (section `## Issues` du
   rapport, ou la ligne de la table de l'Étape 6), jamais leur texte.
4. Écart `Workflow : v` index ↔ version courante : champ `avertissement`, jamais une action.
5. Sortie texte : une ligne lisible puis les champs ; `--json` : l'objet.
6. Tests, une fixture par cas : plan neuf → `regler-effort` puis `lancer` vague 1 · vague faite non
   poussée → `pousser` · close sans revue → `relire` · `validation-humaine` · `exécution` Sonnet →
   `reprendre` Opus · `prémisse` sans mesure → `verifier-premisse` · budget épuisé → `question` ·
   `Auto : oui` → `reprendre` + option · `reprise-manuelle` → `question` · `wave.lock` →
   `question` · tout coché et poussé → `fini`.

### Validation
- **N0 auto** : `node plugin/bin/n0.mjs` → tout PASS ; `node plugin/bin/prochaine-action.mjs P5` → `fini`.
- **Tests** : `tests/tester-scripts.mjs`, les onze cas.
- **Anti-raccourci** : un test qui n'asserte que le **nom** de l'action laisse passer un mauvais
  modèle de reprise — asserter aussi `modele`, `sessions` et `option`.

### Si bloqué
Deux lectures codables d'une règle de `remediation.md` → les écrire au bilan, coder la plus
prudente (celle qui rend `question`). Un défaut du parseur de S2 : correctif localisé, commit séparé.

**Résumé** : `node plugin/bin/prochaine-action.mjs P<n> [--json]` (sans `--etat`) rend maintenant une
action. Ordre : `wave.lock` → `question` · commits locaux en avance sur l'amont → `pousser` ·
première vague non entièrement `faite` : un membre en `echec` → remédiation (budget d'abord, table
de `remediation.md` reprise telle quelle : `Auto : oui` prioritaire, `prémisse` sans/avec `Mesure`,
`environnement`, `exécution` un cran au-dessus plancher Sonnet, `Opus` → enquête sauf `Blocage`
nommant un geste) ; sinon un membre `a-lancer` → `lancer` (`regler-effort` à sa place si aucun commit
`Plan: P<n>/` n'existe encore pour ce plan, vérifié seulement à ce point précis — pas en tête du
script — pour qu'une session déjà en échec ne se fasse jamais devancer par `regler-effort`, voir
« Écart » ci-dessous) ; vague entièrement `faite` : revue manquante (zone non `aucune`, pas
d'`.echec.md`) → `relire`, mais **seulement si l'index porte une ligne `Workflow : v`** — un plan
antérieur à C3/C4 (P4, P5) n'a jamais produit de `.revue.md`, l'exiger rétroactivement serait un état
deviné ; `validation-humaine` si la vague suivante n'a pas démarré ; sinon vague suivante. Boucle
épuisée → `fini`. Écart `Workflow : v` index / version courante (lue dans `plugin.json` du dépôt
source ou `manifest.json` vendoré, best-effort) → champ `avertissement`, jamais une action.

**Écart au plan (à signaler, sans conséquence fonctionnelle)** : l'Étape « Décision clé » de ce
`S10.md` énonce `regler-effort` comme une clause à part après l'ordre principal
(« n'est rendu qu'une fois : aucun commit `Plan: P<n>/` n'existe encore »), lue d'abord comme un
garde-fou global à tester en tête de moteur. Codé ainsi, une session dont la toute première tâche
échoue avant tout commit se serait vue répondre `regler-effort` au lieu de sa remédiation
(`verifier-premisse`/`reprendre`/`enqueter`) — un plan a forcément commencé dès qu'une session a
tourné, échec compris. Corrigé en plaçant la vérification uniquement au point où le moteur s'apprête
à rendre `lancer` (elle ne s'applique donc jamais quand une vague antérieure est encore ouverte par
un échec, une revue manquante ou une validation humaine) : la remédiation d'une session déjà en
échec passe toujours avant. Fixture dédiée (`plan neuf, aucun commit Plan: → regler-effort` /
`un commit Plan: existe déjà → lancer vague 1`) et cas séparé
(`échec exécution, modèle Sonnet → reprendre Opus`) couvrent les deux ordres pour le prouver.

**Budget par plan (2 enquêtes)** : dérivé en sommant `Tentatives : … enquete=` des seules sessions
*actuellement* en `echec` de ce plan — un `.echec.md` disparaît au `PASS` (`/reprendre-echec` Étape
5), c'est tout ce que des fichiers commités peuvent encore dire une fois l'échec résolu. Pas testé
séparément (aucun des onze cas de la Validation ne l'isole) ; le code est écrit et lisible, à
confirmer sur un vrai double échec si l'occasion se présente.

comprise avec ses onze cas neufs) ; `node plugin/bin/prochaine-action.mjs P5` → `fini` ;
