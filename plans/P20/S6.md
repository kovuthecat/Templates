## T9 — Le moteur sait qu'une session attend une réponse

### Objectif
Une session qui tombe sur un choix écrit `plans/P<n>/S<k>.question.md` (gabarit nouveau), le committe,
et rend `VERDICT: QUESTION`. Le moteur en dérive un état `en-attente` et rend :
- sans ligne `Réponse :` remplie → `question` (texte rédigé par S5 : la question, ses options, le
  fichier à relire) ;
- avec réponse → `transmettre` (`session`, `agent` = identifiant gardé dans le fichier, `message` =
  la réponse) ; hors budget : ni reprise ni enquête ;
- avec réponse et ligne `Agent : introuvable` (posée par l'orchestrateur quand `SendMessage` échoue) →
  `reprendre` à froid, dont le prompt fait lire le fichier et sa réponse ; hors budget aussi.
Une session marquée `pastille` dans l'index est lancée comme les autres, avec un `avertissement`.

### Pourquoi
C'est la demande de départ : piloter un plan depuis le téléphone, sans pastille à cliquer. La critique
du plan a relevé qu'aucun état disque ne marquait une session arrêtée sur une question : elle
retombait en « à lancer » (relance à froid) ou en « arbre sale » — et l'identifiant d'agent n'était
connu que de la conversation. Le fichier `.question.md` porte les deux.

### Décision clé
- Gabarit `S<k>.question.md` (lignes mécaniques en tête, comme `.echec.md`) :
  `Question : <une phrase>` · `Fichier à relire : <chemin ou —>` · `Agent : <identifiant>` ·
  `Réponse : —` (remplie par l'orchestrateur avec ta réponse, puis committée) ; puis `## Options`
  (lignes recopiées dans la question) et `## Contexte` (deux lignes au plus).
- Une session qui écrit ce fichier **committe son travail en cours** avant (WIP de tâche, repère
  `Plan:`) : sinon l'arbre sale bloque tout le plan pendant l'attente. Le moteur exclut
  `S<k>.question.md` du contrôle de zone comme les autres fichiers du plan.
- Au `PASS` qui suit la reprise, la session supprime le fichier par un commit (comme un `.echec.md`).
- L'identifiant d'agent : la session ne connaît pas toujours le sien. Si elle ne le connaît pas, elle
  écrit `Agent : —` et l'orchestrateur le complète à la collecte (il le tient de l'appel `Agent`) —
  écrire cette double voie dans le gabarit.
- `pastille` : lu, ignoré, avertissement « marque héritée, lancée en sous-agent ».
- **Le minimum de texte pour que l'arrêt se joue dès maintenant** (le scénario de T10 passe par la
  vraie skill d'orchestration) — S11 et S12 le reformuleront, ici une ligne chacun :
  - `orchestrer-plan/SKILL.md` : une ligne `transmettre` dans la table des actions (« `SendMessage`
    à `agent` avec `message` ; échec → écrire `Agent : introuvable` dans le `.question.md`, committer,
    rappeler le moteur ») ; `QUESTION` ajouté à la ligne `VERDICT:` du prompt de l'Étape 1 ; à la
    collecte d'un `QUESTION`, compléter `Agent :` si la session a écrit `—`.
  - `EXECUTANT.md` : une règle — un choix qui t'arrête (les quatre critères existants) s'écrit dans
    `plans/P<n>/S<k>.question.md` (gabarit), après avoir committé le travail en cours ; puis
    `VERDICT: QUESTION`. Reprise par message : continuer avec la réponse ; au PASS, supprimer le
    fichier par un commit.

## T10 — Le scénario « arrêt relayé », joué avec une vraie attente

### Objectif
Ajouter au banc le scénario `arret-relaye` et un mode **en deux temps** de `lancer.mjs` : un premier
`claude -p` **persisté** joue jusqu'à la question, le banc attend `--attente <minutes>`, puis
`claude -p --resume <id>` envoie la réponse. Le passage est noté par `noter.mjs` (verdict `QUESTION`,
appels `SendMessage`). Puis le jouer une fois avec une attente d'au moins 30 minutes, et consigner
le résultat de H1.

### Pourquoi
H1 (risque déclaré du plan) : « une session reprend par `SendMessage` avec son contexte après une
longue attente » n'a été vérifiée que sans attente (sonde du 2026-10-14). Le banc actuel ne peut pas
la jouer (`--no-session-persistence`, un seul prompt). La jouer ici, et non en S13, évite d'écrire
S11-S12 sur une voie fausse.

### Décision clé
- État posé `arret-relaye` : un plan P1 dont S1 a pour consigne de s'arrêter sur un choix nommé
  (par exemple : deux noms possibles pour une fonction) après avoir lu un fichier et retenu un mot
  qui ne figure pas dans la question. Réponse attendue de la reprise : le mot retenu + le nom choisi.
  C'est ce qui prouve le contexte conservé (même preuve que la sonde du 2026-10-14).
- Deuxième temps : la réponse est écrite dans `S1.question.md` (ligne `Réponse :`) et committée par
  le banc, puis le prompt de reprise relance `/workflow:orchestrer-plan P1` — c'est l'orchestrateur,
  via le moteur (`transmettre`), qui fait le `SendMessage`.
- Résultat de H1 : **confirmée** (mot retenu restitué par la même session) ou **réfutée** (agent
  introuvable, contexte perdu) — dans les deux cas une mesure, pas un échec de la session. Réfutée :
  écrire au bilan, et dans une ligne du `.question.md` du gabarit, que le repli « reprise à froid qui
  lit la réponse » est la voie principale ; S11-S12 le liront.
- `noter.mjs` : verdict `QUESTION` reconnu, appels `SendMessage` comptés (critique, constat 6).

- Modifier : `tests/scenarios/noter.mjs`

### Étapes
1. `--poser-seulement` pose `arret-relaye` ; le moteur rend `lancer` sur S1 (test sans appel à claude).
2. Mode deux temps (`--attente`, `--resume`) ; la persistance n'est activée que pour ce scénario.
3. `noter.mjs` : `QUESTION`, `SendMessage` ; test sur le flux enregistré.
4. Jouer : `node tests/scenarios/lancer.mjs --scenario arret-relaye --autorisations projet --attente 30`,
   puis `node tests/scenarios/noter.mjs -v`. Bilan : identifiant, coût, attente réelle, mot restitué
   ou non, issue du moteur.

### Validation

- **N1 visuel auto** : —

  prouve pas le contexte conservé (la session le relit au lieu de s'en souvenir). Le mot ne doit
