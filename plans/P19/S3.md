## T3 — Un clone à historique partiel est détecté, jamais lu comme complet

### Objectif
Au démarrage, le moteur teste `git rev-parse --is-shallow-repository`. Historique partiel → il
tente `git fetch --unshallow` ; réussi, il continue normalement ; échoué, il rend `question`,
source `historique-partiel`, motif qui cite l'erreur de git et le remède à la main.
`preuve-n0.mjs` ne conclut jamais « valide » ni « invalide » sur un historique partiel : il rend un
motif `historique partiel` distinct.

### Pourquoi
Une session cloud clone avec 50 commits par défaut : les commits de tâche plus anciens deviennent
invisibles, et le moteur peut relancer une session déjà faite ou boucler sur `valider-n0`. Le plan 2
rendra l'orchestration encore plus autonome — elle doit d'abord lire un état vrai.

### Décision clé
- Le `fetch --unshallow` passe par un **appel dédié** (`execFileSync('git', [...])` avec son propre
  délai, **au moins 120 s**, stderr conservé pour le motif), **jamais** par le helper `git()` (délai
  8 s, erreur rendue `null`) : un vrai dépôt sur un réseau de session cloud dépasse 8 s, le fetch
  serait tué et chaque appel rendrait la question.
- Place du test : avant toute lecture de l'historique (`refsCommitees`), après le contrôle « plan
  absent / index illisible ».
- Le motif de la question donne la commande à lancer (`git fetch --unshallow`) et dit que le moteur
  n'a rien conclu sur l'état du plan.

### Lire / Modifier
- Modifier : `plugin/bin/prochaine-action.mjs`
- Modifier : `plugin/bin/preuve-n0.mjs`
- Modifier : `tests/tester-scripts.mjs`

### Étapes
1. Cas de test d'abord : dépôt jetable avec plusieurs commits dont `Plan: P9/S1/T1` loin de la
   pointe ; `git clone --depth 1 file://<dépôt>` ; dans le clone, **origin retiré** → le moteur rend
   `question` source `historique-partiel` ; **origin laissé** (file://) → le fetch réussit et le
   moteur rend la même action que sur le dépôt complet. Constater l'échec du premier cas sur le code
   actuel.
2. Détection + appel dédié dans le moteur ; motif.
3. `preuve-n0.mjs` : même détection (sans fetch) → motif `historique partiel`. Cas : preuve
   vérifiée dans le clone superficiel → ni valide ni invalide, motif cité.

### Validation
- **N0 auto (bloque le commit)** : `node plugin/bin/n0.mjs --session P19/S3` → vert
- **Tests** : clone `--depth 1` sans origin → `historique-partiel` ; avec origin → action normale ;
  `preuve-n0` sur clone superficiel → motif dédié.
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : le `fetch --unshallow` lancé par `git()` (8 s) : il passe le test sur un
  dépôt minuscule et échoue sur un vrai. Le relecteur vérifie l'appel dédié et son délai.

## T4 — Compteurs lus sur tout l'historique, clés sans accent, prémisse vérifiée une fois

### Objectif
1. **Clés normalisées** : `lireEchec` reconnaît une clé quelles que soient sa casse et ses accents
   (`Prémisse`, `Premisse`, `PRÉMISSE`, `Tentatives`, `Nature`, `Mesure`, `Auto`, `Blocage`) —
   même normalisation que les valeurs (`normaliserSimple`).
2. **Compteurs depuis git** : `reprise` et `enquete` d'une session = le **maximum** relevé sur la
   version de l'arbre de travail **et** sur **toutes les versions commitées** du `.echec.md` de
   cette session (y compris celles d'avant sa suppression au PASS).
3. **Enquêtes par plan** = somme, sur **tous** les `plans/P<n>/S*.echec.md` ayant existé dans
   l'historique (présents ou supprimés), de leur maximum d'`enquete`.
4. **`verifier-premisse` une fois par session** : le résultat de la vérification est **toujours**
   écrit dans le rapport, et le moteur ne revérifie jamais une prémisse dont le résultat est écrit :
   - `Premisse : refutee · …` → branche `exécution` (inchangé) ;
   - `Premisse : confirmee · …` → `question`, source `etape6`, cas `premisse-confirmee` (comme une
     mesure commitée) ;
   - `Premisse : indecidable · …` → `question`, cas `premisse-indecidable`, motif qui cite la preuve ;
   - ligne présente, valeur non reconnue → `question`, cas `premisse-illisible` ;
   - ligne absente mais présente dans une version commitée antérieure → `question`, cas
     `premisse-deja-verifiee`.
5. **Consignes alignées** : `reprendre-echec/SKILL.md:47` dit la même chose que `:150` et `:179` —
   la session de reprise ou d'enquête incrémente `Tentatives :`, le moteur prend le maximum sur
   l'historique ; `remediation.md` § `verifier-premisse` : pour `CONFIRMEE` et `INDECIDABLE`,
   ajouter la ligne `Premisse : confirmee · <preuve>` / `Premisse : indecidable · <preuve>` et
   committer **avant** de poser la question, comme pour `REFUTEE`.

### Pourquoi
Les garde-fous anti-boucle reposent aujourd'hui sur des lignes recopiées à la main : une ligne
`Prémisse : réfutée` (accent) fait boucler le moteur sur `verifier-premisse` (reproduit), le budget
d'enquêtes par plan repart de zéro dès qu'un échec est résolu, et une prémisse confirmée se fait
revérifier à la relance suivante. Un orchestrateur Haiku qui recopie doit pouvoir se tromper de
graphie sans faire boucler le plan.

### Décision clé
- « Compteurs calculés depuis git » (décision du 2026-10-14, point 3) se lit ici comme : le
  **maximum sur l'historique** des valeurs écrites, pas la dernière valeur. Une reprise qui remet
  `reprise=0` ou supprime le fichier ne remet plus le budget à zéro.
- **Revers assumé, à écrire dans le commentaire du budget** : une reprise qui **oublie**
  d'incrémenter reste non comptée. Le correctif complet — le moteur écrit lui-même le compteur —
  est le point 10b du plan 2.
- Lecture de l'historique : `git log --format=%H -- <chemin>` puis `git show <h>:<chemin>` (absent
  au commit de suppression → ignoré). Pour la somme par plan, lister les chemins par
  `git log --format= --name-only -- plans/P<n>/` filtré sur `S\d+\.echec\.md$`. Passer par `git()`
  (opérations locales, 8 s suffisent).
- Les deux lignes ajoutées à `remediation.md` sont une **mécanique** (le même geste que pour
  `REFUTEE`), pas une règle de plus : sans trace écrite, le moteur ne peut pas savoir qu'une
  vérification a déjà eu lieu.

## T5 — Une relecture sans `Couverture :` est à refaire

### Objectif
`lireRevue` rend `couverture: 'invalide'` dès que la ligne `Couverture :` manque, même si
`Bloquant :` est présent (aujourd'hui : `complète` par défaut, l.364). L'en-tête du moteur (l.19-22)
dit exactement ce qui est lu dans l'arbre de travail (index et `[x]`, `.echec.md`, `.revue.md`,
`wave.lock`) et ce qui est lu dans git (commits de tâche, revue supprimée). Recherche, dans les
projets voisins, des relectures que ce changement ferait refaire.

### Pourquoi
Une relecture écrite sur une ligne, au format de la réponse du relecteur, passe aujourd'hui pour
complète : la session est considérée relue alors que personne n'a écrit la revue. Le revers : une
vieille revue sans ce champ, dans un plan encore ouvert d'un projet, sera relue une fois de plus
après la 0.66.0 — d'où la recherche, pour que ce coût soit connu avant publication.

### Décision clé
- En-tête : aligner le **texte** sur le code, pas l'inverse (le code lit l'arbre de travail pour de
  bonnes raisons : `[x]` d'une vague verrouillée, rapport d'échec pas encore commité).
