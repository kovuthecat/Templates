## T9 — Chaque suite une fois en N0, plus de copie du plugin oubliée

### Objectif
- `publier.mjs` accepte `--sans-tests`, **seulement avec `--dry-run`** : il saute alors
  `tester-hooks`, `tester-renvois`, `tester-scripts`, `tester-preuves` et garde tout le reste
  (synchro git, payload, scan des chemins personnels). Seul, `--sans-tests` est refusé (sortie 1,
  « rien publié »).
- `.claude/n0.json` : `publier-dry-run` lance `--dry-run --sans-tests`, et `tester-preuves` y entre
  comme commande à part (il n'y tournait que par le dry-run).
- Aucune sortie de `publier.mjs` placée après la création du dossier temporaire (l.300) ne le
  laisse derrière elle : `process.exitCode` + `return` (ou exception rattrapée) au lieu de
  `process.exit` dans le `try`, pour **toutes** les sorties (l.310, l.323, l.353, l.359).

### Pourquoi
La N0 de ce dépôt dure environ deux minutes, dont la moitié à relancer des suites déjà passées ; et
chaque passage laisse une copie de `plugin/` dans le dossier temporaire, parce que `process.exit`
saute le `finally`. Toutes les sessions du workflow paient cette N0.

### Décision clé
- **La publication réelle teste toujours tout** : `node plugin/bin/publier.mjs` sans argument ne
  change pas (l'en-tête l.27-31 fait de ces tests la condition d'entrée de toute publication) —
  d'où le refus de `--sans-tests` seul.
- `--dry-run` seul garde son comportement actuel (tout tester) : quelqu'un qui le lance à la main
  veut savoir si une publication passerait.
- Ordre dans `n0.json` : `tester-hooks`, `tester-scripts`, `tester-renvois`, `tester-preuves`,
  `tester-mods`, `publier-dry-run`.

### Lire / Modifier
- Modifier : `plugin/bin/publier.mjs`
- Modifier : `.claude/n0.json`
- Modifier : `tests/tester-scripts.mjs`

### Étapes
1. Mesurer d'abord : `node plugin/bin/n0.mjs` → noter la durée de chaque commande (sortie
   `nom → PASS (x.xs)`), et le nombre de dossiers `claude-workflow-publier-*` dans le dossier
   temporaire du système.
2. Cas de test : `publier.mjs --sans-tests` seul → sortie 1, message « rien publié » ;
   `--dry-run --sans-tests` → ne lance aucune des quatre suites (leur marqueur de sortie absent) ;
   `--dry-run` lancé avec `TMPDIR`/`TEMP`/`TMP` pointés vers un dossier jetable → dossier vide à la
   fin ; une sortie d'échec **dans** le `try` (chemin personnel planté dans une copie jetable du
   dépôt, si `publier.mjs` s'y lance — il se situe par `import.meta`) → sortie 1, dossier
   temporaire vide. Si la copie jetable s'avère impossible (dépendance au vrai `origin`), le dire au
   bilan avec la raison, et garder les trois autres cas.
3. `publier.mjs` : `--sans-tests`, sorties sans fuite.
4. `n0.json`.
5. Remesurer : `node plugin/bin/n0.mjs` → durées, et aucun nouveau dossier
   `claude-workflow-publier-*`. Les deux mesures au bilan.

### Validation
- **N0 auto (bloque le commit)** : `node plugin/bin/n0.mjs --session P19/S5` → vert, six commandes
- **Tests** : les quatre cas de l'étape 2.
- **N1 visuel auto** : —

## T10 — Les suites déterministes tournent en CI

### Objectif
`.github/workflows/plugin.yml` lance les suites qui ne dépendent ni du réseau ni d'une connexion
`claude` (au moins `tester-hooks`, `tester-scripts`, `tester-renvois`, `tester-preuves` ;
`tester-mods` s'il tient sans `claude` connecté), et se déclenche aussi sur `tests/**`. Un passage
de CI réel est observé vert, puis rouge sur une casse provoquée.

### Pourquoi
La CI ne vérifie aujourd'hui que la syntaxe, le manifeste et l'inventaire : un push qui casse un
comportement passe vert. C'est le filet de tout ce que le plan 2 va simplifier.

### Décision clé
- Une suite écrite pour Windows qui échoue sous Linux se **rend portable** (chemins, séparateurs,
  `process.platform`) ; un cas qui ne peut tourner que sous Windows est sauté **par cas**, avec un
  `SKIP <nom> — Windows seulement` visible dans la sortie, jamais par suite entière.
- Une suite qui exige `claude` connecté ou le réseau reste hors CI, motif en commentaire dans le
  YAML.
- Gate observé, pas supposé : branche jetable `ci-p19-sonde` poussée telle quelle → run vert ; un
  commit qui casse un cas → run rouge ; puis branche supprimée sur le dépôt distant et en local.
  `gh run watch <id>` pour suivre chaque run (une fois par run, pas d'attente en boucle).

### Lire / Modifier
- Modifier : `.github/workflows/plugin.yml`
- Modifier : `tests/tester-scripts.mjs`
- Modifier : `tests/tester-hooks.mjs`
- Modifier : `tests/tester-renvois.mjs`
- Modifier : `tests/tester-preuves.mjs`
- Modifier : `tests/tester-mods.mjs`

Les cinq suites ne se modifient que pour la portabilité Linux, et seulement si un cas casse en CI.

### Étapes
1. Ajouter les étapes au YAML et `tests/**` aux `paths` de `push` et `pull_request`.
2. Pousser `ci-p19-sonde` ; corriger la portabilité jusqu'au vert (chaque correction sur la branche).
3. Commit de casse (un `assert` inversé dans un cas) → run rouge observé ; le retirer.
4. Reporter les corrections de portabilité sur `main` (commit de la tâche) ; supprimer la branche
   (`git push origin --delete ci-p19-sonde`, `git branch -D ci-p19-sonde`).
5. Après le push de `main` : `gh run list --workflow plugin.yml --branch main --limit 1` → vert.

### Validation
- **N0 auto (bloque le commit)** : `node plugin/bin/n0.mjs --session P19/S5` → vert
- **Tests** : les suites existantes, en CI ; aucun cas nouveau.
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : un run vert obtenu en sautant des cas. Le bilan cite, pour chaque suite, le
  nombre de cas passés en CI contre le nombre en local, et chaque `SKIP` avec sa raison ; et les
  identifiants des deux runs de la branche jetable (vert, rouge).

### Si bloqué
