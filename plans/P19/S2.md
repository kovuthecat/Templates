## T2 — Une dérive reste signalée, un manifeste abîmé arrête la mise à jour

### Objectif
Quatre corrections de `sync-workflow.mjs`, chacune avec son cas de test :
1. un fichier DÉRIVE garde dans le manifeste le **hash connu** (celui du dernier contenu écrit
   depuis la source), au lieu du hash du disque ;
2. un fichier obsolète (sorti du payload) n'est supprimé que s'il est propre (disque == hash
   connu) ; modifié localement, il est **gardé**, signalé DÉRIVE, et **reste dans le manifeste**
   avec son hash connu — `--force` le supprime ;
3. un manifeste illisible (JSON invalide) arrête le script en sortie 2, avec un message qui nomme
   le fichier et dit quoi faire — jamais traité comme un manifeste vide ;
4. un fichier binaire est reconnu par extension élargie **ou** par la présence d'un octet NUL dans
   ses premiers 8 Ko, dans `sync-workflow.mjs` **et** dans la copie de `publier.mjs` (l.85).

### Pourquoi
La promesse de `/maj-workflow` est qu'une modification locale n'est jamais écrasée en silence. La
revue a reproduit l'inverse : signalée au 2ᵉ passage, écrasée au 3ᵉ. Un projet qui a modifié un
fichier du workflow le perd sans le savoir.

### Décision clé
- **Pas de « dérive conservée » durable** : `/maj-workflow` n'offre que Remonter (porter la
  modification dans la source) ou Écraser (`--force`). Une dérive est donc un état à trancher, qui
  doit revenir à chaque passage tant qu'il ne l'est pas. Garder le hash connu suffit : au passage
  suivant, disque ≠ hash connu → DÉRIVE à nouveau. C'est la raison pour laquelle le format du
  manifeste ne change pas.
- **Obsolète modifié localement : reste suivi** (choix de l'utilisateur, 2026-10-14) — même logique
  que les autres dérives ; le revers accepté est que le signal se répète jusqu'à l'arbitrage.
- Manifeste illisible : sortie **2** (le script utilise déjà 1 pour `--check` avec action due et 3
  pour un cache périmé). Message : chemin du manifeste, « illisible », et le remède (le restaurer
  depuis git, ou relancer avec `--force` en sachant que toute dérive locale sera écrasée).
- Liste d'extensions binaires : ajouter au moins `pdf`, `webp`, `avif`, `bmp`, `tiff?`, `ttf`,
  `otf`, `eot`, `mp3`, `mp4`, `webm`, `wav`, `ogg`, `gz`, `tar`, `7z`, `wasm`. Le test d'octet NUL
  rattrape le reste.

### Étapes
1. Écrire d'abord le cas « trois passages » (dossier jetable : sync → modification locale d'un
   fichier géré → sync → sync) et constater qu'il **échoue** sur le code actuel (la modification
   disparaît au 3ᵉ passage) — c'est la preuve que le test couvre le bug.
2. Corriger l.372-377 : pour un DÉRIVE, reporter le hash connu dans `nouveauxHashes`. Le cas passe.
3. Obsolète : avant `rmSync` (l.370), comparer disque et hash connu ; modifié → ne pas supprimer,
   signaler DÉRIVE, garder l'entrée et son hash connu dans le manifeste (sauf `--force`). Cas :
   fichier retiré du payload et modifié localement → présent après deux passages, signalé aux deux ;
   avec `--force` → supprimé. Cas : retiré et propre → supprimé (comportement actuel conservé).
4. Manifeste : `try/catch` autour du `JSON.parse` (l.297) → sortie 2 et message. Cas : manifeste
   `{` → sortie 2, aucun fichier du projet écrit (comparer l'arbre avant/après).
5. Binaires : extension élargie + octet NUL, dans les deux scripts. Cas : un `.pdf` et un fichier
   sans extension contenant un octet NUL, synchronisés → identiques octet pour octet à la source.
6. Ligne de `/maj-workflow`.
