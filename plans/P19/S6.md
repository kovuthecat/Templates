## T11 — Un harnais qui joue un plan réel de bout en bout

### Objectif
Créer `tests/scenarios/` : une commande (`node tests/scenarios/lancer.mjs --scenario <nom>
[--essais <n>]`) qui pose un mini-projet jetable dans le dossier temporaire du système, y fait
dérouler `/workflow:orchestrer-plan P1` par un vrai `claude -p` jusqu'à la fin, puis note le
passage (`node tests/scenarios/noter.mjs`). Quatre scénarios, chacun un **état posé** :

| Scénario | État posé | Première action attendue du moteur |
| --- | --- | --- |
| `nominal` | plan P1 neuf, deux sessions d'une tâche chacune | `lancer` S1 |
| `echec-reprise` | S1 a échoué : `S1.echec.md` `Nature : exécution`, `Tentatives : reprise=0 enquete=0`, test rouge commité | `reprendre` S1 |
| `interruption` | S1 a deux tâches, T1 commitée (`Plan: P1/S1/T1`), T2 non, pas de rapport d'échec | `relancer-interrompue` S1 |
| `revue-incomplete` | S1 faite, `S1.revue.md` avec `Bloquant : 0` sans `Couverture :` | `relire` S1 |

### Pourquoi
Le banc actuel ne note que le **premier geste** de l'orchestrateur sur un état préparé, et les
évaluations `plugin/evals/` sont figées en v0.39.0. Les gains annoncés par le plan 2 (agents
d'effort retirés, moteur qui écrit, plans plus courts) ne seront que des estimations sans un coût
mesuré **par plan terminé**, avant et après.

### Décision clé
- **Mini-projet réaliste** : construit à partir de `plugin/templates/` (fichiers de contexte
  minimaux) et **vendoré** par `sync-workflow.mjs` depuis un instantané de `plugin/` copié hors du
  mini-projet ; N0 du mini-projet = un `node test.mjs` sans dépendance ; tâches triviales et
  déterministes (ajouter une fonction et son cas de test). Sessions en `Haiku · medium` pour
  contenir le coût.
- **`origin` = dépôt nu local** (`git init --bare` dans le dossier jetable), `main` poussée avec son
  amont : une session pousse en fin de session et le moteur rend `pousser` selon l'amont. Sans lui,
  chaque push échouerait et compterait comme intervention. (Exception n°1 au README du banc, qui
  retire `origin`.)
- **Hooks actifs** : les hooks du plugin chargé par `--plugin-dir` tournent (pas de
  `disableAllHooks`) — c'est le comportement réel (Stop, garde-fou git) qu'on mesure. (Exception
  n°2.)
- Pièges gardés : variables `CLAUDE_CODE_*`, `CLAUDECODE`, `DISABLE_MICROCOMPACT` retirées ;
  `GIT_CONFIG_GLOBAL` jetable et identité git locale ; `--strict-mcp-config` ;
  `--no-session-persistence` ; `--plugin-dir` vers l'instantané (alerte si l'événement `init` ne le
  montre pas).
- Orchestrateur : `--model haiku --effort medium` (`WORKFLOW.md` §3). Permissions :
  `--permission-mode acceptEdits` et `--allowedTools` explicite (au moins `Read Edit Write Glob Grep
  Agent SendMessage Skill Bash(git:*) Bash(node:*)`) — **jamais `bypassPermissions`** : le
  mini-projet tourne sur le vrai poste de l'utilisateur. Un outil refusé pendant la mise au point
  s'ajoute à la liste, nommé au bilan.
- Chaque scénario **vérifie la première action du moteur avant tout `claude -p`** (table ci-dessus,
  `prochaine-action.mjs P1 --json` dans le mini-projet) : un autre résultat est une fixture à
  corriger, pas un attendu à ajuster (même règle que `poser-cas.sh`).
- Mesures par passage, lues par `noter.mjs` dans le `stream-json` et l'état final :
  - **coût** : `total_cost_usd`, `num_turns`, durée, et `modelUsage` par modèle ;
  - **interventions humaines** : nombre de `question` rendues (un `claude -p` s'arrête sur la
    première ; attendu 0) ;
  - **relances inutiles** : lancements `Agent` d'une session déjà faite au moment du lancement ;
  - **preuves valides** : chaque `S<k>.n0.json` vérifié par `preuve-n0.mjs` ;
  - **issue** : action du moteur sur l'état final — attendu `fini`.
- **H2** (Risques du plan) se vérifie ici : `modelUsage` contient-il le modèle des sessions en plus
  de celui de l'orchestrateur ? Réponse au bilan et dans la mesure.

## T12 — La mesure de référence

### Objectif
Jouer les **5 passages mesurés** (nominal ×2, `echec-reprise`, `interruption`, `revue-incomplete`)
et écrire `docs/analyses/2026-10-14-mesure-de-reference.md`.

### Pourquoi
C'est le chiffre sur lequel le plan 2 sera écrit et jugé : « coût total par plan terminé » avant
simplification. Sans lui, chaque économie du plan 2 reste une estimation.

### Décision clé
- Contenu exigé de l'analyse (c'est le seul livrable qui restera) :
  1. contexte : date, commit du dépôt mesuré, version du plugin, version de Claude Code, modèles ;
  2. une ligne par passage : scénario, coût, tours, durée, sessions lancées, relances inutiles,
     questions, preuves valides, issue ;
  3. écart entre les deux passages `nominal` (la variance à dépasser pour qu'un gain du plan 2
     compte) ;
  4. réponse à **H2** (le coût inclut-il les sous-agents) ;
  5. **sonde du point 9**, recopiée de la section ci-dessous ;
  6. constats pour le plan 2 : chaque défaut vu pendant un passage, avec le scénario ;
  7. la commande exacte pour rejouer la mesure en fin de plan 2.
- **Sonde du point 9 (faite le 2026-10-14 par le cadreur, Claude Code 2.1.293)** — à recopier telle
  quelle : depuis la conversation principale, `Agent({ subagent_type: "workflow:session-high",
  model: "haiku", effort: "low", run_in_background: false })`, alors que le frontmatter de
  `session-high` porte `effort: high` et que la conversation tournait en `high`. Transcription du
  sous-agent (`~/.claude/projects/<projet>/<conversation>/subagents/agent-<id>.jsonl`) : ses tours
  portent `"effort":"low"`, et le fichier `.meta.json` porte `"effort":"low"`. Contrôle : un agent
  lancé dans la même conversation sans paramètre `effort` (`analyste-flux`, sans `effort` en
  frontmatter) porte `"effort":"high"`, celui de la conversation. **Conclusion : positive** — le
  paramètre `effort` de l'outil `Agent` est appliqué et prime le frontmatter de l'agent. Non testé :
  depuis un sous-agent (session) qui lance son propre sous-agent ; sous Claude Code < 2.1.292.
  Suite : plan 2 (retrait des agents `session-<effort>`, `WORKFLOW.md` §3 et §5b à corriger — ils
  disent que seule `CLAUDE_CODE_EFFORT_LEVEL` bat le frontmatter).
