## T6 — `git add` analysé argument par argument, `--amend` n'exempte plus `-a`

### Objectif
Dans `pretooluse-git.mjs`, le refus du staging global ne dépend plus de la position de l'argument.
Pour chaque segment `git [-C x | -c k=v]… add|stage …` : refuser si un argument est `.`, `./`,
commence par `:` (pathspec magique : `:/`, `:(top)`…), est `-u`/`--update`, `-A`/`--all`, une
option courte groupée qui contient `A` ou `u` (`-Av`, `-uv`), ou un **joker qui ne désigne aucun
chemin réel**. `git commit … -a …` est refusé même avec `--amend`.

### Pourquoi
La revue a reproduit que `git add src/a.ts .`, `git add -- .`, `git add :/`, `git add -u`,
`git add *` et `git commit --amend -a` passent : le motif exige que `.` suive immédiatement `add`,
et `--amend` désactive le contrôle de `-a`. Un staging global embarque dans le commit d'une tâche des
fichiers d'une autre.

### Décision clé
- **Joker** : un argument contenant `*`, `?` ou `[` n'est refusé que s'il ne désigne **aucun chemin
  littéral existant** (sur le disque, relatif au `cwd` du hook et à un éventuel `-C`) —
  `git add app/[id]/page.tsx` (routes Next.js, SvelteKit) reste accepté. Les guillemets d'un
  argument sont **retirés, pas vidés** : `git add '*.md'` (joker développé par git lui-même) est
  refusé. Ne pas réutiliser `neutraliserTexte` pour `add` : il vide le texte entre guillemets, c'est
  fait pour les messages de commit.
- Les options après `--` sont des chemins : `git add -- .` est refusé au titre de `.`.
- `git stage` est un alias de `git add` : même analyse.
- Le message de refus actuel est gardé, en ajoutant la forme refusée.

### Lire / Modifier
- Lire : `plugin/hooks/pretooluse-git.mjs` — en entier (108 lignes).
- Modifier : `plugin/hooks/pretooluse-git.mjs`
- Modifier : `tests/tester-hooks.mjs`

### Étapes
1. Cas de non-régression d'abord, constatés rouges sur le code actuel : refusés —
   `git add src/a.ts .`, `git add -- .`, `git add ./`, `git add :/`, `git add -u`, `git add -Av`,
   `git add '*.md'`, `git add *` (sans fichier nommé `*`), `git stage .`,
   `git commit -am msg --amend`, `git commit --amend -a -m x`. Acceptés —
   `git add app/[id]/page.tsx` (fichier créé dans le dépôt de test), `git add plans/P19/`,
   `git add f.txt g.txt`, `git commit --amend -m x`, `git commit -m "fix: git add . refusé"`.
2. Analyse par argument ; retrait de l'exemption `--amend`.
3. Tous les cas existants de `pretooluse-git` restent verts sans être modifiés.

## T7 — `/purge-contexte` pousse, `/revue-de-conception` peut committer

### Objectif
`/purge-contexte` pousse son commit en fin de skill. `/revue-de-conception` reçoit
`Bash(git add:*)`, `Bash(git commit:*)`, `Bash(git push:*)` dans `allowed-tools`, `Bash` sort de
`disallowed-tools` (`PowerShell` y reste), et son texte dit que `Bash` n'y sert qu'à ces trois
commandes.

### Pourquoi
Le hook Stop refuse une fin de tour avec des commits d'avance : `/purge-contexte`, déclenchée par un
hook, se fait ensuite refuser par un autre ; `/revue-de-conception` exige un commit qu'elle ne peut
pas faire, faute de `Bash`.

### Décision clé
- Premier geste : agent `lecteur-doc`, au premier plan (`run_in_background: false`), sur la doc des
  skills de Claude Code — syntaxe admise des motifs `Bash(<commande>:*)` dans `allowed-tools` d'une
  skill, et si `allowed-tools` **restreint** les outils ou seulement les **pré-autorise**. Résultat
  et URL au bilan.
- Le frontmatter visé est le même dans les deux cas ; seul le sens de la phrase du texte change :
  restriction → « la skill ne peut lancer que ces trois commandes » ; pré-autorisation seule →
  « n'utilise `Bash` que pour ces trois commandes » (consigne). Si la syntaxe à motif n'est pas
  admise : `allowed-tools` reçoit `Bash` nu, même phrase de consigne.
- `/revue-de-conception` « ne modifie pas de code » : cette intention est tenue par le texte et par
  le fait que la skill n'écrit que son rapport et la décision ; `Bash` ne la change pas.

## T8 — Un plugin installé en retard est signalé au démarrage, doublon de casse compris

### Objectif
Dans le dépôt source, au démarrage d'une session, `sessionstart-contexte.mjs` signale toute entrée
`workflow@templates` de `installed_plugins.json` qui vise ce dépôt avec une version plus ancienne
que `plugin/.claude-plugin/plugin.json`. Quand plusieurs entrées visent ce dépôt à la casse près
(`C:\Users\kovu\…` et `C:\Users\Kovu\…`), le signal nomme l'entrée en retard comme **doublon**, avec
son chemin et sa version, et donne un remède qui la **retire** — pas `plugin update`.

### Pourquoi
Ce poste est resté en 0.55.0 pendant que le dépôt passait à 0.65.0, sans signal (constat du
2026-10-14). Cause trouvée à l'investigation : deux entrées locales, une par casse du chemin ;
`publier.mjs` ne met à jour que celle de la casse courante. Un poste qui déroule une vieille
version en croyant éditer la dernière corrige des bugs déjà corrigés.

### Décision clé
- **Fait établi le 2026-10-14** : `installed_plugins.json` contient `workflow@templates` scope
  local, `projectPath: "C:\\Users\\kovu\\Projets\\Templates"` en 0.55.0 (lastUpdated 2026-10-06) et
  `"C:\\Users\\Kovu\\Projets\\Templates"` en 0.65.0.
- **Un contrôle existe déjà** (l.190-221) : « plugin chargé ≠ source », fondé sur `ICI`, présent
  aussi dans le cache 0.55.0. Pourquoi il n'a rien dit n'est pas établi : c'est la **sonde** du
  premier geste, et elle décide d'un seul point — la visibilité (étape 3).
- Comparaison des chemins **insensible à la casse seulement pour un chemin à lettre de lecteur**
  (`^[A-Za-z]:[\\/]`) : sur Linux, deux casses sont deux dossiers. Testable sur Linux (CI de S5).
- Lecture de `installed_plugins.json` : même lecteur que le bloc des mods (l.247-258 :
  `CLAUDE_CONFIG_DIR` ou `~/.claude`), sans lancer de processus (budget du hook), muet sur toute
  erreur de lecture.
- Remède du doublon : celui que la sonde établit (étape 1b). Ne jamais l'exécuter sur ce poste.
