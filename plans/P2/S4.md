## T11 — Écrire `.claude/skills/nouveau-projet/SKILL.md`

### Objectif
Une skill qui EST le questionnaire de cadrage : interview guidée → PROJECT_BRIEF rempli →
instanciation mécanique des fichiers → prochaines étapes annoncées. Rien d'oublié au démarrage
d'un projet, zéro coût tant qu'elle n'est pas invoquée.

### Décision clé
Validé en conversation : skill plutôt que fichier questionnaire vierge. Le questionnaire vit DANS
la skill et s'enrichit d'une ligne à chaque oubli constaté en projet réel. L'interview se mène
question par question (une à la fois, pas un mur de questions) ; les réponses alimentent
directement les fichiers. La liste des fichiers copiés et le contenu du stub AGENTS.md sont repris
du README actuel — la skill devient la source, le README pointera vers elle (S8).

### Lire / Modifier
Créer : `.claude/skills/nouveau-projet/SKILL.md`.

### Étapes
1. Frontmatter : name `nouveau-projet` ; description = « Démarrer un projet : interview de cadrage
   guidée (questionnaire complet) puis instanciation des fichiers de contexte, settings et git.
   À dérouler avec Opus dans le futur repo vide, avant toute autre chose. »
2. **Phase A — Interview** (ordre imposé, une question à la fois, reformuler la réponse en 1 ligne
   avant de passer à la suivante) :
   1. Problème & objectif — qu'est-ce qui est pénible aujourd'hui, à quoi ressemble « réussi » ?
   2. Utilisateurs & contexte d'usage — qui, sur quel appareil, à quelle fréquence ?
   3. Fonctionnalités MVP — 3 à 7, formulées en verbes ; pour chacune : indispensable au jour 1 ?
   4. Hors-périmètre explicite — ce qu'on refuse de faire au MVP (au moins 3 items).
   5. Plateformes cibles — desktop / mobile / PWA ; conditionne les contraintes UI.
   6. Données — entités principales, volumétrie, besoin multi-appareil ? (→ oriente persistance :
      local-first Dexie vs Supabase, cf. habitudes des projets existants).
   7. Stack — défaut Vite+React+TS sauf raison contraire ; toute déviation = pourquoi en 1 ligne.
   8. Contraintes — offline, accessibilité, ton visuel, perf.
   9. **Stratégie de test (obligatoire, pas optionnelle)** — runner (vitest en devDep par défaut),
      quelles logiques pures seront testées dès le MVP ; « aucun test » doit être justifié et
      consigné dans DECISIONS.
   10. UI ou pas — détermine si `DESIGN_SPEC.md` est copié et si l'étape maquette existe.
   11. Nom du projet + emplacement du repo.
3. **Phase B — Restitution** : synthèse ≤ 15 lignes, validation de Thibault AVANT d'écrire quoi
   que ce soit.
4. **Phase C — Instanciation mécanique** : copier les fichiers listés au README §Copiés (+
   `DESIGN_SPEC.md` si UI) ; `project-settings.json` → `.claude/settings.json` ; stub `AGENTS.md`
   (bloc du README) ; remplir `PROJECT_BRIEF.md` avec les réponses ; supprimer les sections
   template non pertinentes ; `git init` + premier commit (`chore: instanciation projet depuis
   Templates`).
5. **Phase D — Annonce des étapes suivantes** (sans les exécuter) : ARCHITECTURE (avec Opus) →
   DESIGN_SPEC + maquette Claude Design (si UI) → `/nouveau-plan` P1 → CLAUDE.md commandes réelles
   + vérif typecheck non vide + `.claude/launch.json`.
6. Longueur cible : ≤ 120 lignes.

### Validation

  README §Copiés (+ DESIGN_SPEC conditionnel) — comparer ligne à ligne.
