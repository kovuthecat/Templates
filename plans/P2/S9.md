## T24 — Installer la marketplace et le plugin en local

### Objectif
Le plugin `workflow@templates` installé au scope utilisateur depuis le repo local.

### Décision clé
Installation depuis le CHEMIN local (pas GitHub) : le repo n'est pas encore poussé, et le test
GitHub/cloud vient après le push de fin de plan. Scope utilisateur : les skills du workflow
doivent exister partout, y compris dans un repo vide au moment de `/nouveau-projet`.

### Lire / Modifier
Modifier : configuration `~/.claude/` (via CLI uniquement — pas d'édition manuelle de fichiers).

### Étapes
1. Vérifier la syntaxe réelle : `claude plugin --help` (et sous-commandes).
2. `claude plugin marketplace add <chemin local du repo Templates>`.
3. `claude plugin install workflow@templates` au scope utilisateur.
4. `claude plugin details workflow@templates` (ou équivalent) → consigner ce qui est chargé
   (skills, agents, hooks) et le coût always-on affiché s'il l'est.

### Validation
- **N0 auto** : la commande de détails liste bien 6 skills, 4 agents, 4 hooks.
- **N1** : — · **N2** : —

### Si bloqué
Erreur d'installation → copier le message exact, STOP. Ne pas « réparer » en déplaçant des
fichiers du repo.

## T25 — Vérifier le chargement réel (smoke tests)

### Objectif
Preuve que skills, hooks, agents et injection CLAUDE-BASE fonctionnent via le plugin.

### Décision clé
Tester dans un répertoire de test JETABLE (hors Templates, hors projets réels) contenant un
`.claude/settings.json` copié de `project-settings.json` — c'est le chemin qu'empruntera chaque
projet migré.

### Lire / Modifier
Rien dans le repo (répertoire de test temporaire uniquement).

### Étapes
1. Créer le répertoire de test + settings + `git init` + un fichier factice.
2. `claude -p "Liste tes skills disponibles et tes agents"` → les 6 skills et 4 agents du plugin
   apparaissent.
3. `claude -p "Quelles règles communes as-tu reçues en début de session ?"` → les règles
   CLAUDE-BASE sont citées (injection SessionStart OK) et UNE seule fois.
4. Test hook git : `claude -p "Exécute: git add -A"` → refus par le hook (message du
   pretooluse-git).
5. Test agent : `claude -p "Utilise l'agent explorateur pour trouver le fichier factice"` →
   délégation effective, réponse compacte.
6. Consigner chaque résultat (commande → constat) dans le rapport de session ; supprimer le
   répertoire de test.

### Validation
- **N0 auto** : les 5 constats ci-dessus sont PASS. Un seul FAIL → T26 n'est pas lancée.

## T26 — Retirer les jonctions (après gate humaine)

### Objectif
Fin de l'ancien mécanisme : plus de jonctions NTFS `~/.claude/skills/<nom>` → Templates.

### Décision clé
**Ne s'exécute qu'après relecture du rapport T24-T25 par Thibault.** Les jonctions sont des liens
(les sources dans Templates restent intactes) — réversible en les recréant, mais on ne supprime
pas un mécanisme qui marche avant la preuve que son remplaçant marche.

### Lire / Modifier
Modifier : `~/.claude/skills/` (suppression des jonctions vers Templates uniquement).

### Étapes
1. Lister les jonctions : `dir ~/.claude/skills` → identifier celles pointant vers Templates
   (attendu : nouveau-plan, verif-visuelle, fin-de-tache, purge-contexte).
2. Supprimer CES jonctions uniquement (`Remove-Item` sur le lien, pas la cible).
3. Re-tester : `claude -p "Liste tes skills"` dans le répertoire d'un projet migré → les skills
   du workflow apparaissent encore (via plugin), sans doublon.
4. S'il existe dans `~/.claude/settings.json` des entrées devenues obsolètes (permissions liées aux
   jonctions) : les signaler dans le rapport, ne PAS les modifier.

### Validation
- **N0 auto** : skills toujours disponibles post-suppression, zéro doublon dans la liste.
- **N1** : — · **N2** : validation finale Thibault sur le rapport complet de la session.

### Si bloqué
Un doublon ou une absence apparaît → recréer la jonction supprimée (rollback), STOP, rapport.
